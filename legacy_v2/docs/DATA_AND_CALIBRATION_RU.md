# Данные и калибровка ROS 2 room world model v2

В v2 запись камеры содержит время из V4L2 и явный интервал возможного начала наблюдения. Действия для обучения берутся из подтверждённых MCU событий START/STOP. Прежде чем учить динамику, нужно связать эти две временные линии и измерить геометрию: иначе модель будет обучаться на неверных парах «картинка — действие — следующая картинка».

Рабочий режим первой комнаты — короткий импульс, подтверждение выключения PWM, ожидание физического успокоения, новое наблюдение и следующее решение. Начальная текстовая цель — приблизиться к **единственному видимому человеку**, сохранив дистанцию, по наблюдаемому свободному пути. Монокулярная depth model остаётся эмпирическим источником геометрии. Неизвестный участок нового footprint, потеря цели и неоднозначные данные означают остановку.

Все команды ниже запускаются из корня проекта в его Python-окружении. Команды `calibrate` не управляют приводом; `latency-record` переключает только явно выбранный GPIO светодиода. Для одновременной работы двух владельцев одной камеры поддержки нет: перед отдельной калибровкой остановите Pi capture node и другие приложения, открывшие устройство. Полученные отчёты сохраняют `accepted=false` и не включают двигатели.

## 1. Временная модель: наблюдение, доставка и исполнение

### 1.1. Какие часы и метки используются

| Поле или событие | Смысл | Как используется |
|---|---|---|
| `v4l2_timestamp_ns` | Метка из `v4l2_buffer.timestamp` при `VIDIOC_DQBUF` | Интерпретируется только вместе с `v4l2_flags` и типом часов |
| `timestamp_clock` | `MONOTONIC`, `UNKNOWN` или `COPY` | Только MONOTONIC напрямую сопоставим с монотонными часами того же Pi |
| `timestamp_source` | `SOE`, `EOF` или `EMPIRICAL` | Определяет способ построения интервала |
| `dequeue_mono_ns` | Время Pi сразу после получения буфера | Точка отсчёта возраста и диагностики очереди |
| `exposure_earliest_ns`, `exposure_latest_ns` | Нижняя и верхняя границы времени начала наблюдения | Основные временные данные для safety, replay и экспорта |
| `timing_valid`, `timing_evidence_id` | Наличие принятого измерения и идентификатор отчёта | Без них неизвестное время не становится допустимым для движения |
| `read_duration_s` | Длительность ожидания/чтения API | Диагностика; не длительность экспозиции и не возраст кадра |
| `ready_mono_s` | Завершение декодирования на Pi | Дополнительная задержка после получения буфера |
| `exposure_estimate_s` | Середина принятого интервала; при неизвестном времени — delivery placeholder | При `timing_valid=false` использовать для обучения и разрешения движения нельзя |
| MCU START/STOP ticks | Начало и прекращение применения PWM по часам Arduino | Длительность действия; отдельно сохраняется неопределённость положения действия на временной линии Pi |

`read_mono_s` сохранён как совместимое имя для времени доставки: у прямого V4L2 это `dequeue_mono_ns / 1e9`. Нельзя подставлять сюда завершение inference. Поле ROS `Header.stamp` служит оценкой в ROS/system time для инструментов просмотра и bags; Pi проверяет свежесть по исходным monotonic границам. У кадра с неизвестным временем header не выдаётся за аппаратную экспозицию.

`time.monotonic()` на Pi и на ПК имеет разные начала отсчёта. Нельзя вычислять «возраст» как `pc_monotonic - pi_monotonic`. ПК возвращает идентификатор кадра, а Pi сопоставляет ответ со своей записью. Собственную длительность inference ПК может измерять локально. Семантика V4L2 timestamp, масок часов и SOE/EOF описана в [документации Linux](https://docs.kernel.org/userspace-api/media/v4l/buffer.html); получение буфера — в [VIDIOC_DQBUF](https://docs.kernel.org/userspace-api/media/v4l/vidioc-qbuf.html).

### 1.2. Три варианта границ

Пусть `t` — метка драйвера, `d` — Pi dequeue time, `ε` — измеренная ошибка метки, `T` — верхняя граница экспозиции, считывания и задержки постановки EOF. В формулах используются секунды; в сообщениях сохраняются целые наносекунды.

| Режим | Интервал начала наблюдения | Что требуется измерить |
|---|---|---|
| MONOTONIC SOE | `[t − ε, min(d, t + ε)]` | Верность SOE-семантики данного драйвера и ошибка метки |
| MONOTONIC EOF | `[t − T − ε, min(d, t + ε)]` | Ошибка метки и весь путь от начала экспозиции до EOF, включая software timestamp delay |
| EMPIRICAL | `[d − Lmax, d − Lmin]` | Оптическая задержка того же camera pipeline; обычно принимается только `Lmin=0` |
| Нет принятого измерения | Обе границы `null`, `timing_valid=false` | Такой кадр пригоден для диагностики/просмотра, не доказывает свежесть |

Нижняя граница ограничивается нулём часов Pi. Верхняя оценка возраста на Pi в момент `now` равна:

\[
A_{upper}=now-t_{earliest}.
\]

Метод `CaptureTiming.age_upper_ns(now_pi_mono_ns)` реализует эту проверку. Монотонная метка далеко в будущем считается ошибкой; наличие EMPIRICAL fallback не маскирует её. Источник SOE/EOF сам по себе не доказывает точность драйвера. Интервал относится к началу наблюдения; rolling shutter и движение во время формирования изображения остаются дополнительными причинами использовать кадры после физического успокоения.

### 1.3. Настройки по умолчанию и критерии принятия

```yaml
camera:
  backend: v4l2
  pixel_format: MJPG
  buffer_count: 4
  stall_timeout_s: 2.0
  max_capture_age_at_dequeue_s: 1.0
  max_training_exposure_uncertainty_s: 0.10
  timing:
    accepted: false
    timestamp_uncertainty_s: null
    exposure_readout_bound_s: null
    empirical_latency_bound_s: null
    empirical_latency_min_s: 0.0
    evidence_id: ""
```

Это шаблон, не результат измерения. `max_capture_age_at_dequeue_s` — допустимый предел для safety gate; он не доказывает, что камера действительно укладывается в него. `timestamp_uncertainty_s`, `exposure_readout_bound_s` и `empirical_latency_bound_s` заполняются измерениями, подходящими именно выбранному режиму. `evidence_id` связывает настройки с сохранённым отчётом. Принятое время требует `accepted=true` и непустого evidence ID; этот флаг меняется после оценки реальных данных, а не ради снятия отказа.

В v2 старые примерные `capture_latency_estimate_s` и `capture_latency_bound_s` из v1 не используются камерой как основание для принятого времени. Вызов `make_frame` со старыми positional latency arguments остаётся технически допустимым, но создаёт **непринятое** время. Изменение номера версии старого JSON не восстанавливает отсутствующие измерения.

## 2. Прямой V4L2 захват и диагностика очереди

### 2.1. Реализованный backend

`camera_v4l2.py` поддерживает 64-битный Linux x86_64/aarch64, single-planar `VIDEO_CAPTURE`, MMAP, progressive frames, MJPG и YUYV. Подходящая целевая среда Pi — 64-битная ОС. Multiplanar, interlaced и другие форматы требуют отдельного адаптера; автоматического незаметного перехода на OpenCV нет. Смена драйвером запрошенного размера/формата либо существенно другого FPS приводит к отказу, чтобы не применять калибровку другого режима.

Поток захвата постоянно возвращает буферы драйверу и оставляет только самый новый raw frame. Отдельный поток декодирует последний доступный raw frame. Между камерой и inference нет FIFO из всех пропущенных изображений: при отставании заменяются старые неиспользованные кадры. Это ограничивает очередь приложения; фактическую внутреннюю задержку камеры всё равно нужно измерять. Механизм MMAP соответствует [V4L2 Streaming I/O](https://docs.kernel.org/userspace-api/media/v4l/mmap.html).

Прямой probe использует настройки `camera` из конфигурации:

```bash
python -m room_world_model.calibrate v4l2-probe \
  --config config/robot.yaml \
  --frames 120 --warmup 5 \
  --output measurements/v4l2_probe.json
```

В отчёте проверьте `device`, `timestamp_clocks`, `timestamp_sources`, `raw_v4l2_flag_values`, `dequeue_interval_ms`, `dequeue_minus_native_timestamp_ms` и отдельные записи кадров. Число dequeue minus timestamp зависит от того, означает метка SOE или EOF; при EOF оно не включает всё время экспозиции. `optical_exposure_latency_measured=false` остаётся false: этот probe читает драйвер, но не видит внешнее событие с известным временем.

Опциональное `camera.controls` задаёт integer V4L2 controls: `exposure_auto`, `exposure_auto_priority`, `exposure_absolute`, `focus_auto`, `focus_absolute`, `autogain`, `gain`, `auto_white_balance`, `white_balance_temperature`. Единицы и допустимые значения определяются драйвером. Заданные значения устанавливаются и читаются обратно; несовпадение вызывает отказ. Без этого блока утилита не выбирает экспозицию произвольно. Доступные текущие значения сохраняются в `device.controls_readback`. Автоэкспозиция может менять фактическое формирование кадра при другом освещении; проверка начала сессии не наблюдает непрерывно все внутренние решения камеры.

### 2.2. OpenCV fallback и длительность read

На среде без поддерживаемого прямого V4L2 можно явно выбрать `camera.backend: opencv`. Этот путь не получает аппаратные flags и формирует только EMPIRICAL интервалы при наличии принятой оптической калибровки. V4L2 control mapping с ним не применяется. Установка `CAP_PROP_BUFFERSIZE=1` не является доказательством отсутствия очереди: свойства проходят через backend, драйвер и устройство, как отмечено в [OpenCV VideoCapture](https://docs.opencv.org/4.x/d8/dfe/classcv_1_1VideoCapture.html).

Старый диагностический probe оставлен именно для времени API:

```bash
python -m room_world_model.calibrate probe \
  --device /dev/video0 --backend v4l2 \
  --width 640 --height 480 --fps 15 --frames 100 \
  --output measurements/opencv_read_probe.json
```

Здесь `--backend v4l2` означает OpenCV CAP_V4L2, а не прямой новый драйвер. `--display` включает окно при наличии OpenCV GUI. Полученные `read_duration_ms` и `read_end_interval_ms` не заполняют calibration bounds. Для получения raw V4L2 flags используйте отдельную команду `v4l2-probe` выше.

## 3. Оптическая калибровка задержки с LED на том же Pi

### 3.1. Подготовка

Установите светодиод в поле зрения камеры и подключите его через подходящий токоограничивающий резистор к свободному GPIO Pi с общей землёй. Номер `--gpio-pin` — **BCM numbering**, не номер контакта на разъёме. `17` ниже — пример; сначала проверьте, что эта линия не занята другой частью робота. Камера остаётся неподвижной, питание/управление приводом в этом опыте не используется.

Нужны `gpiozero` и работающий pin factory для данного Pi. Для Pi 5 в официальной таблице gpiozero указан `lgpio`; [таблица backend](https://gpiozero.readthedocs.io/en/stable/api_pins.html) и [установка](https://gpiozero.readthedocs.io/en/stable/installing.html) объясняют зависимость от системы и окружения. Пример для отдельного Python-окружения проекта:

```bash
python -m pip install gpiozero lgpio
export GPIOZERO_PIN_FACTORY=lgpio
```

Доступ к локальному GPIO должен быть настроен на ОС Pi. Collector не использует удалённый GPIO: camera dequeue и отметки переключения должны относиться к одним часам Pi. Mock pin factory подходит для программных тестов, но не является физическим измерением задержки.

Выберите небольшую ROI, в которой средняя интенсивность BGR явно различается между выключенным и включённым светодиодом. Порядок аргументов — `X Y WIDTH HEIGHT`. Например, `270 190 40 40` допустим для 640 × 480, но эти координаты нужно заменить координатами своего светодиода. По умолчанию состояние OFF распознаётся при средней интенсивности не выше 60, ON — не ниже 180; пороги задаются `--off-max` и `--on-min`. Если LED занимает лишь маленькую часть тёмной ROI, уменьшите ROI или измерьте подходящие пороги.

### 3.2. Две независимые серии

```bash
python -m room_world_model.calibrate latency-record \
  --config config/robot.yaml \
  --gpio-pin 17 --roi 270 190 40 40 \
  --split fit --session latency_fit_day1 \
  --condition daylight_idle \
  --events 40 \
  --csv-output measurements/latency_fit.csv \
  --output measurements/latency_fit_report.json
```

```bash
python -m room_world_model.calibrate latency-record \
  --config config/robot.yaml \
  --gpio-pin 17 --roi 270 190 40 40 \
  --split check --session latency_check_day2 \
  --condition low_light_cpu_usb_load \
  --events 40 \
  --csv-output measurements/latency_check.csv \
  --output measurements/latency_check_report.json
```

Строка `--condition` только описывает условия. Она не затемняет комнату и не создаёт CPU/USB-нагрузку: эти условия нужно действительно воспроизвести. Несколько дополнительных fit/check сессий можно передать в одну команду fitting, если camera mode один и тот же.

Collector случайно выбирает промежутки между переключениями из `[0.5, 1.5]` секунды, чтобы не синхронизироваться постоянно с одной фазой кадров. `--min-hold-s`, `--max-hold-s` и `--seed` настраивают это поведение. После каждой смены он ждёт визуальное подтверждение; следующий переход не происходит, пока предыдущий не наблюдался. По умолчанию требуется два последовательных подходящих кадра, но в CSV записывается время **первого** кадра этой серии. `--event-timeout-s` по умолчанию 8 секунд. Превышение timeout означает ошибку измерения, ROI или канала, а не разрешение выбрать удобную маленькую задержку. При ошибке уже записанная часть CSV сохраняется.

Для каждого события сохраняются интервал вызова GPIO (`event_earliest_ns`, `event_latest_ns`), `first_seen_dequeue_ns`, frame sequence, raw V4L2 metadata, состояние LED, `session`, `split`, `condition` и `camera_mode_id`. Работа заканчивается выключением LED и освобождением камеры/GPIO. В программе нет команд к Arduino.

### 3.3. Fit, held-out проверка и применение отчёта

```bash
python -m room_world_model.calibrate latency-fit \
  --csv measurements/latency_fit.csv measurements/latency_check.csv \
  --fps 15 \
  --extra-frame-periods 2 --extra-margin-s 0.05 \
  --output measurements/camera_timing_report.json
```

`--fps` должен соответствовать калибруемому режиму. Запас 0.05 секунды в примере — выбранный инженерный параметр, а не измеренная характеристика камеры. Минимум по умолчанию — 20 наблюдений в каждой независимой части. Верхняя оценка отдельного события вычисляется по разности `first_seen_dequeue_ns - event_earliest_ns`. Она включает неопределённость команды GPIO и ожидание подходящей фазы кадра. Кандидат общей границы:

\[
L_{candidate}=\max_{i\in fit} L_i+\frac{2}{FPS}+margin.
\]

Контрольные данные не используются для расширения кандидата. Если хотя бы одна check-задержка больше кандидата, `empirical_holdout_pass=false` и `suggested_timing_config=null`. При успешной проверке отчёт содержит `evidence_id` и `suggested_timing_config` с `accepted=false`, `empirical_latency_min_s=0`. Он не выводит положительный минимум задержки и не подбирает из LED-данных точные ошибки нативного SOE/EOF. Копировать нужно весь согласованный блок, сохраняя исходные CSV/JSON; окончательное принятие основывается на физических измерениях.

Одна сессия не может одновременно быть fit и check. Дубликаты наблюдений и смешанные `camera_mode_id` отклоняются. Camera-mode hash связывает разрешение, format, FPS, backend, заданные controls и доступные данные драйвера/устройства. Он не удостоверяет неизменность внешнего освещения, монтаж камеры, правильность проводки и все скрытые режимы устройства. Новая камера, кодек, разрешение или принципиально другой режим экспозиции требуют новых измерений. После подгонки параметров по неудачной check-серии понадобится новая независимая check-серия.

Отчёт содержит median, p95, p99 и максимум; p99.9 выводится только при наличии как минимум 1000 наблюдений. Эти числа описывают измеренную выборку. Будущий максимум может оказаться больше, особенно при другой экспозиции или нагрузке. Съёмка телефона одновременно физического LED и экрана может быть дополнительной проверкой end-to-end задержки, но измеряет также сеть и отображение; она не заменяет привязку кадра к Pi dequeue time.

### 3.4. Почему калибровка задержки ещё не означает пригодность для world model

В конфигурации `camera.max_training_exposure_uncertainty_s=0.10`. Это предел **половины ширины** интервала:

\[
u=\frac{t_{latest}-t_{earliest}}{2}\leq0.10\text{ с}.
\]

Проверка действует при экспорте обучающих переходов и обновлении recurrent state. Большой, но честный EMPIRICAL интервал иногда достаточен для медленного safety-контроля и всё ещё слишком неопределёнен для точного обучения динамики. Например, при `Lmax=0.8` с и `Lmin=0` половина ширины равна 0.4 с: соответствующие переходы не допускаются в обучение с текущим порогом. Это нормальный диагностический результат.

Чтобы получить полезные данные, нужно уменьшить реальную временную неопределённость: разобраться с нативной меткой SOE/EOF, отдельно измерить её ошибку и необходимый exposure/readout bound либо изменить видеорежим и повторить оптический опыт. Малое время inference и большое ожидание между импульсами сами по себе не сужают неизвестное время экспозиции. Нельзя выдавать примерный timestamp за точный только для увеличения числа `valid_transitions`.

## 4. Геометрия камеры и корпуса

Калибровка объектива, положение камеры на корпусе и погрешность depth model — три отдельные задачи. Нельзя получить все три, сфотографировав шахматную доску один раз.

### 4.1. Intrinsics и искажения объектива

Подготовьте плоскую доску с чёткой шахматной сеткой. Параметры `--cols` и `--rows` означают количество **внутренних углов**, а не клеток. Для 9 × 6 внутренних углов прямоугольник содержит 10 × 7 клеток. Измерьте реальный размер клетки в метрах после печати; масштабирование принтером меняет его.

Начальный практический набор — 20–30 резких фотографий доски с разными наклонами, расстояниями и положениями по полю зрения. Это предлагаемая процедура сбора, а не гарантированное достаточное количество. Доска должна появляться у краёв и в углах изображения. Повторение почти одинакового центрального ракурса мало добавляет к геометрии. Используйте то же разрешение 640 × 480, тот же режим объектива и фокус, что в работе.

```bash
python -m room_world_model.calibrate intrinsics \
  --images measurements/chessboard_raw \
  --cols 9 --rows 6 --square-size-m 0.025 \
  --output measurements/intrinsics.json \
  --camera-config-output measurements/camera_intrinsics_only.json
```

Утилита вызывает `findChessboardCornersSB`, при необходимости стандартный поиск с `cornerSubPix`, затем `calibrateCamera` и `getOptimalNewCameraMatrix`. Она сохраняет параметры искажений, матрицу для исправленного изображения, ошибку репроекции для каждого снимка и шаблон `CameraCalibration`. Все операции соответствуют публичному API OpenCV. [Калибровка камеры в OpenCV](https://docs.opencv.org/4.x/dc/dbb/tutorial_py_calibration.html), [API calib3d](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html).

По умолчанию используется `alpha=0`, сохраняются прежние размеры изображения, дополнительное обрезание не выполняется. `camera_intrinsics_only.json` содержит `fx`, `fy`, `cx`, `cy` уже для исправленной картинки. Положение камеры, радиус робота и погрешности глубины в нём всё ещё примерные; `accepted` остаётся `false`.

Проверка результата проводится на дополнительных фотографиях доски: прямые линии должны оставаться прямыми, края изображения не должны изгибаться неправдоподобно. Число RMS само по себе недостаточно. При объективе с выраженным fisheye эта реализация стандартной pinhole-калибровки может оказаться неподходящей; менять несколько коэффициентов наугад нельзя.

### 4.2. Одинаковое исправление изображения при разметке и исполнении

Сырые RGB используются для сохранения исходных данных. World model получает уменьшенную до 128 × 128 чёрно-белую версию того же сырого кадра и при обучении, и при инференсе. Для semantic perception создаётся отдельная исправленная RGB-копия. Таким образом, разметка и реальное исполнение должны применять один и тот же `intrinsics.json`.

```python
from room_world_model.calibrate import ImageRectifier
from room_world_model.perception import CameraCalibration

camera = CameraCalibration.from_json("config/camera.json")
rectifier = ImageRectifier("config/intrinsics.json")
rectifier.validate_calibration(camera)

rgb_rectified = rectifier(rgb_raw)
observation = perception.observe(
    rgb_rectified,
    original_timestamp_ns,
    image_valid_mask=rectifier.valid_mask,
)
```

Исправление не меняет временную метку. `valid_mask` запрещает трактовать недействительные края remap как наблюдаемое пространство. `validate_calibration` проверяет совпадение разрешения и матрицы. Если поток уже исправлен самим устройством, повторное исправление делать нельзя: нужно использовать параметры именно этого выходного потока и явно отметить его происхождение.

### 4.3. Положение камеры и размеры робота

Запишите измеренные параметры в `config/camera.json`. Система координат: `x` вперёд, `y` влево, `z` вверх. Положительный `camera_pitch_down_rad` означает наклон вниз. Камера считается направленной вдоль продольной оси; боковой yaw/roll этим прототипом не моделируется.

| Поле | Что измерить |
|---|---|
| `camera_height_m` | Высота оптического центра над плоским полом |
| `camera_pitch_down_rad` | Наклон оптической оси вниз в радианах |
| `camera_forward_m` | Смещение камеры вперёд относительно центра модели корпуса; сзади значение отрицательное |
| `camera_left_m` | Смещение камеры влево; справа значение отрицательное |
| `robot_radius_m` | Радиус окружности, содержащей весь корпус, включая выступы |
| `robot_height_m` | Высота части корпуса, которая может столкнуться с предметами |
| `obstacle_margin_m` | Дополнительный геометрический запас |
| `floor_tolerance_m` | Допуск определения пола; увеличение скрывает всё более низкие предметы |

При прямоугольном корпусе радиус должен покрывать углы, а не только половину ширины. Здесь используется окружность: это консервативнее прямоугольного footprint, зато проще проверять поворот. Колёса, провода, выступающие платы и камера входят в физический габарит.

Проекция строится из глубины вдоль оптической оси `Z`:

```text
x_ray = (u - cx) / fx
y_ray = (v - cy) / fy
forward = camera_forward + Z * (cos(pitch) - sin(pitch) * y_ray)
left    = camera_left    - Z * x_ray
height  = camera_height - Z * (sin(pitch) + cos(pitch) * y_ray)
```

Это используемая в коде геометрия, а не обучаемое предположение. Проверьте несколько меток на полу рулеткой: близко, далеко, слева, справа. Если после изменения наклона камеры такой же пиксель означает другое место пола, требуется новая extrinsics-калибровка.

### 4.4. Почему свободный центр кадра ещё не разрешает поворот

Для каждого предлагаемого `(v, w)` функция `path_clearance` проверяет весь новый участок, который займёт увеличенная окружность корпуса. Она использует точки возможных препятствий с запасом на погрешность глубины и проецирует образцы новой площади корпуса обратно в изображение. Неизвестный пол, край кадра или ближняя слепая зона приводят к отказу.

У обычной фронтальной USB-камеры часть площади рядом с бортами и непосредственно перед корпусом может не попадать в кадр. Тогда даже при большом `clearance_center` функция вернёт `swept_footprint_enters_camera_blind_region`. Это существенный результат проверки расположения камеры, а не ошибка порога, которую следует отключить.

Камера выше на мачте с подходящим наклоном или другой объектив могут улучшить обзор пола, но одновременно ухудшить видимость человека. Выдвижение камеры вперёд не всегда помогает боковым слепым зонам. Нужно проверять реальную проекцию корпуса и затенение корпусом самой камеры. `path_clearance` выполняет дискретную инженерную проверку в пределах монокулярной модели; она не доказывает отсутствие стекла, тонких проводов или скрытых поверхностей.

Если геометрия не покрывает новую занимаемую площадь, текущий режим должен оставаться неподвижным. Практическое следующее улучшение — обзор ближней зоны или независимые датчики расстояния/контакта. Обучение world model не даёт новых наблюдений там, где камера физически ничего не видит.

## 5. Метрическая глубина и её эмпирическая погрешность

В проекте выбран `depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf`: официальный indoor checkpoint, дообученный для метрической глубины. Его конфигурация содержит `depth_estimation_type: metric`; библиотечный адаптер это проверяет. Используется числовой `predicted_depth`, а не цветная картинка из визуализирующего pipeline. [Карточка модели](https://huggingface.co/depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf), [конфигурация checkpoint](https://huggingface.co/depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf/blob/main/config.json).

Слово metric означает целевую шкалу предсказания. Оно не обещает требуемую точность на твоём объективе, высоте камеры и комнате. Поэтому измеряется симметричный интервал:

\[
Z_{low}=\max(0,sZ_{pred}(1-r)-a),\qquad
Z_{high}=sZ_{pred}(1+r)+a.
\]

Здесь `s` — поправка масштаба, `r` — относительная часть ошибки, `a` — абсолютная часть в метрах. Обе стороны нужны: ошибочно маленькая глубина тоже может испортить отделение пола от препятствия. Для человека и clearance используется нижняя оценка расстояния. Эти интервалы — выбранная и проверяемая модель остаточной ошибки; нейросеть не выдаёт сертификат такого интервала.

Соберите измерения объектов на нескольких расстояниях, включая близкие к требуемой дистанции остановки. Нужны матовые поверхности, обычная мебель и пол, края объектов, одежда человека, разные положения по кадру и освещение. Прозрачные и отражающие поверхности следует отдельно помечать как случаи, где монокулярная оценка может быть недостоверной.

CSV должен иметь столбцы:

```csv
predicted_m,reference_m,session,split
1.15,1.00,depth_day1_layout_a,fit
2.30,2.00,depth_day1_layout_a,fit
1.05,1.00,depth_day2_layout_b,check
2.20,2.00,depth_day2_layout_b,check
```

Это пример формата с вымышленными числами, не набор измерений для принятия калибровки. Утилита требует как минимум 10 реальных измерений в каждой части; разумный эксперимент обычно требует существенно больше и покрытия разных объектов.

`reference_m` — истинная глубина **вдоль оптической оси камеры**, а не расстояние по полу и не произвольное расстояние рулетки. Для известного расстояния по лучу нужно пересчитать `Z = range / sqrt(1 + x_ray² + y_ray²)`. У наклонённой камеры расстояние вдоль пола отличается и от этой величины. Для калибровки удобно применять доску в известных положениях или вычисленную из геометрии осевую координату меток.

```bash
python -m room_world_model.calibrate depth \
  --csv measurements/depth_pairs.csv \
  --absolute-error-m 0.05 --extra-relative-margin 0.05 \
  --camera-config config/camera.json \
  --camera-config-output measurements/camera_depth_candidate.json \
  --output measurements/depth_report.json
```

Указанные запасы в команде — пример, который необходимо выбрать по данным. Поправка масштаба и относительная часть вычисляются только на `fit`. Сессии `check` полностью отделены; одна сессия не может находиться в обеих частях. Если хотя бы одна контрольная точка выходит за интервал, новый camera config не создаётся. Даже успешная проверка сохраняет `accepted: false`: это эмпирическая проверка, а не автоматическое разрешение двигателей.

После подбора по неудачному `check` нужна новая контрольная сессия. Иначе контрольная выборка постепенно становится частью подбора. Смена модели, разрешения, исправления объектива или положения камеры также делает старую проверку недостаточной.

## 6. Сбор сырой истории и экспорт world-model данных

### 6.1. Что записывать и как называть сессии

Первыми можно делать записи без привода: предметы переставляются, человек входит и выходит из кадра, проверяется RGB perception. Такая запись полезна для диагностики, но отсутствие MCU в ней не доказывает нулевые действия робота. Экспортёр подтверждённой динамики требует handshake и полную историю привода.

Для динамики нужны короткие движения под непосредственным контролем оператора после калибровки камеры, привода, корпуса и остановки. Демонстрации могут включать прямые импульсы и видимые свободные дуги. Случайные столкновения не нужны как источник обучающей обратной связи. Перед ручным переносом выполните STOP, дождитесь полной физической остановки и штатно завершите Pi-процесс/запись; затем перенесите робот и запустите новую запись. У ручного движения нет подтверждённых wheel/PWM данных, поэтому оно не должно оказаться внутри перехода, размеченного как нулевой PWM.

Перед новой независимой записью согласованно задайте путь и идентификаторы:

```yaml
runtime:
  record_session: sessions/room_day2_layout_b
session:
  session_id: room_day2_layout_b
  layout_id: layout_b
  day_id: day2
  lighting_id: evening_lamp
  operator: iulian
```

Остальные runtime поля сохраняются из рабочей конфигурации: этот фрагмент не является полной конфигурацией запуска. `layout_id` описывает фактическую расстановку предметов, `day_id` — день сбора, `lighting_id` — условия света. Не присваивайте каждой копии того же проезда новый layout только ради прохождения разбиения. Имя `operator` — необязательная запись происхождения; оно не участвует в моторной авторизации.

Внутри сессии `EpisodeRecorder` создаёт отдельный `episode_id`, состоящий из UTC-времени и случайного суффикса. `session_manifest.json` фиксирует метаданные и конфигурацию сессии; повторное открытие того же каталога с изменённым manifest отклоняется. Для новых физических условий создайте новый `record_session`. Pi boot session и camera epoch в идентификаторе кадра — отдельные технические сущности, которые меняются при перезапуске. Они не заменяют `layout_id` или исследовательский `session_id`.

| Файл внутри записи | Содержимое |
|---|---|
| `sessions/SESSION/session_manifest.json` | Постоянная конфигурация сессии и исследовательские ID |
| `sessions/SESSION/EPISODE_ID/metadata.json` | Версия схемы, происхождение, камера/робот, fingerprint, `log_complete` |
| `sessions/SESSION/EPISODE_ID/events.jsonl` | Кадры, задания, предложенные действия, MCU события, ошибки и границы эпизода |
| `sessions/SESSION/EPISODE_ID/rgb/CAMERA_EPOCH_SEQUENCE.jpg` | Исходный цветной JPEG; его относительный путь есть в событии кадра |

Запись создаётся Pi-узлом автоматически. Подготовку ROS interfaces и запуск Pi/PC смотрите в [README](../README.md) и [руководстве оператора](OPERATING_RU.md). В v2 можно закончить текущий эпизод и открыть следующий через сервис, когда робот разоружён и нет незавершённого MCU импульса:

```bash
ros2 service call /roomwm/new_episode std_srvs/srv/Trigger '{}'
```

Сервис `new_episode` предназначен для границы при неподвижном роботе: он сразу начинает следующий episode и не приостанавливает запись. Вызов только после ручного переноса не делает предыдущие кадры переноса известным нулевым действием. Сам новый episode не даёт разрешение на движение; после возобновления нужны новые observation/context и явный цикл задания/arm. Для новых физических условий меняются также `record_session` и соответствующие ID. Записи камеры с потерянной свежестью, несколько людей, закрытая камера, перестановки и обрывы сети полезны для оценки отказов; выполнять физически опасное действие ради такого теста не требуется.

### 6.2. Подтверждённое действие и проблема «пустой истории»

Для пары `image_t → image_t+1` требуются действия между их экспозициями. World model получает **применённые** нормированные setpoints через упорядоченные сегменты; пожелание планировщика и факт отправки serial-пакета не доказывают исполнение. V2 сохраняет MCU START/STOP, boot ID, nonce, sequence, времена приёма на Pi, измеренную в MCU ticks длительность и интервальные границы её положения на Pi.

Нельзя объявить весь промежуток остановкой только потому, что список импульсов пуст. Программа должна знать, с какого момента она единолично владеет приводом и получила подтверждение PWM-off. `motor_ready` с `zero_confirmed=true` и `exclusive_pulse_firmware=true` устанавливает эту границу. Сбой, reboot или неизвестный исход импульса обрывает покрытие. После них нужен новый подтверждённый zero handshake.

Если handshake закончился после того, как кадр уже попал в очередь, `history_start_s` может оказаться позже camera dequeue. Такая запись не подгоняется под удобный прошлый timestamp: кадр сохраняется с честной границей, а переход без покрытия отклоняется. Период до первого handshake тоже не считается нулевым действием.

Подтверждение MCU означает «PWM применялся/выключен», а не «колесо имело измеренную скорость» и не «корпус полностью остановился». Без encoder feedback остаточное качение, инерция, батарея и скольжение не наблюдаются этой схемой. После PWM-off всё ещё требуется измеренный settling/braking interval. Примерный oscillator-rate bound MCU в конфигурации тоже не заменяет измерение частоты или энкодеры.

### 6.3. Экспорт сырой записи

После корректного завершения Pi-процесса или закрытия эпизода `metadata.json` должен содержать `log_complete=true`. В случае переполнения очереди записи, ошибки диска или незавершённого writer эпизод не принимается как полная история. Не исправляйте этот флаг вручную.

```bash
python -m room_world_model.record \
  --session sessions/room_day2_layout_b \
  --output data/exported
```

Команда находит завершённые эпизоды внутри указанной сессии и создаёт отдельные `.npz`. Для каждого нужны хотя бы четыре `settled` кадра с `timing_valid=true`, полный журнал, zero handshake и однозначные пары отправленных/завершённых импульсов по `(boot_id, nonce, seq)`. Отсутствие завершения или дублирование ключа — отказ экспорта, а не нулевой action. Если только часть временных переходов непригодна, файл сохраняет их с `transition_valid=false`.

Основные поля NPZ:

| Поле | Назначение |
|---|---|
| `images` | Сырой канал камеры, уменьшенный до grayscale 128 × 128 для world model |
| `rgb_paths` | Пути к исходным цветным JPEG для teacher perception; RGB не заменяется увеличенным grayscale |
| `timestamps`, `dt` | Средние точки принятых exposure intervals и интервалы между ними |
| `exposure_earliest_ns`, `exposure_latest_ns` | Исходные наносекундные границы кадра |
| `action_segments`, `segment_mask` | Упорядоченные `[forward, yaw, duration_s]`, включая нулевые паузы |
| `actions` | Среднее по времени действие для аудита; не основной вход recurrent transition |
| `transition_valid` | Пригодность каждого перехода для training windows |
| `aux`, `aux_mask` | Semantic targets и известность значений; после raw export ещё пустые |
| `metadata_json` | `schema_version=2`, происхождение, ID, fingerprint, хеш raw events и семантика действий |

Пример перехода за две секунды: 0.50 с PWM-off, 0.08 с подтверждённого импульса, 1.42 с PWM-off. Это три сегмента, а не две секунды слабого постоянного движения. Нулевой сегмент означает отсутствие PWM; инерционное движение может продолжаться и должно быть представлено скрытым состоянием/измеренными ограничениями.

Экспортёр и runtime filter проверяют, что exposure interval не пересекает неопределённую границу действия. Переход также отклоняется при превышении допустимой временной полуширины 0.10 с, разрыве complete history, смене Pi session/camera epoch, episode boundary, слишком большом `dt` или превышении числа сегментов. По умолчанию `max_dt_s=5.0`, число сегментов не больше 24; loss не должен пересекать недопустимый переход.

RGB остаётся отдельными файлами. При переносе `.npz` нужно переносить и изображения с сохранением относительных путей; команда разметки корректирует ссылки при записи нового NPZ в другой каталог. Не удаляйте сырой events log и RGB после успешного training: они нужны для проверки тайминга и teacher labels.

### 6.4. Разбиение по сессиям и перестановкам

Для `train/validation/test` нужны как минимум три независимые группы. Стандартный `--split-by layout` объединяет связанные записи с общим layout и не делит один session ID. Если одна сессия связывает несколько layouts, вся связанная группа остаётся целой. Разбиение по `day` проверяет перенос между днями, по `session` — между сессиями; это разные проверки обобщения. Пересечения по оставшимся осям, например освещению, выводятся в split audit и не выдаются за unseen условия.

| Часть | Как использовать |
|---|---|
| Train | Обучение world model на нескольких реальных сценах и действиях |
| Validation | Выбор checkpoint, ранняя остановка и настройка параметров |
| Test | Отложенная оценка после фиксации модели; не выбирать по ней лучший checkpoint |

Соседние кадры одного проезда, копии эпизода с другими именами и одинаковый recorded content не становятся независимыми test данными. Photometric augmentation может менять яркость/контраст, но random crop, warp и зеркальное отражение требуют согласованного изменения геометрии и связанных действий. Не отражайте картинку, сохранив прежний знак yaw/bearing и прежние left/right targets.

## 7. Разметка RGB и ручные исправления

YOLO11n используется как детектор категории person. Официальный API возвращает bounding boxes и confidence; это не идентификация того, кто написал сообщение. В этой версии обнаружение двух человек либо неуверенного второго человека делает цель неоднозначной. [YOLO11](https://docs.ultralytics.com/models/yolo11/), [Ultralytics prediction API](https://docs.ultralytics.com/modes/predict/).

```bash
python -m room_world_model.label data/exported/episode.npz \
  --output data/labeled/episode.npz \
  --config config/robot.yaml
```

`--config` задаёт единственный источник camera calibration, исправления RGB, detector, metric depth, revision и `depth_scale_m`. Утилита сверяет fingerprint записи с этой конфигурацией до загрузки моделей, затем проверяет соответствие реально созданного teacher. Индивидуальные флаги `--calibration`, `--intrinsics-json`, `--already-rectified`, `--detector-weights`, `--depth-model`, `--depth-model-revision` и `--depth-scale-m` вместе с `--config` отклоняются, чтобы не смешать настройки. При успехе metadata получает `label_fingerprint_verified=true`. Training сохраняет этот признак; live loader требует его для всех использованных эпизодов.

Модели должны быть заранее доступны локально. Для разметки используют ту же конфигурацию и подготовленные веса, что для runtime. Уже исправленный RGB требует соответствующей исправленной матрицы в `camera.json`, пустого `camera.intrinsics_file` и `camera.already_rectified=true`: повторное исправление не требуется. Старый исследовательский интерфейс с отдельными `--calibration` и остальными флагами остаётся доступен без `--config`; такая новая teacher-разметка всегда получает `label_fingerprint_verified=false`, даже если раньше файл имел проверенный флаг. `--allow-model-download` существует только в этом отдельном интерфейсе. Частичные ручные исправления с неизменным масштабом сохраняют прежний флаг; сами по себе они не превращают непроверенную teacher-разметку в проверенную.

Fingerprint общей конфигурации включает `depth_model_id`, optional `depth_model_revision` и логическое имя detector. В `config/robot.yaml` можно закрепить `perception.depth_model_revision` на конкретном commit checkpoint; этот параметр передаётся загрузчику, runtime и teacher с `--config`. Имя каталога кэша и абсолютный путь весов могут отличаться на Pi и ПК. Для detector по умолчанию сравнивается имя файла, например `yolo11n.pt`; при собственной модели следует задать стабильный `detector_model_id`. Подмена содержимого под тем же именем автоматически не обнаруживается: проверка контрольных сумм всего пакета весов остаётся отдельной подготовкой, большие веса на Pi для этого не читаются.

Учитель читает `rgb_images` или `rgb_paths`. При наличии только 128 × 128 grayscale он отказывается молча подменять полноценное RGB наблюдение увеличенной картинкой. Исходные изображения, действия и интервалы сохраняются. Если `.npz` переносится в другую папку, относительные пути RGB пересчитываются.

Целевые признаки:

| Индекс | Признак | Значение и маска |
|---|---|---|
| 0 | `person_visible` | Есть единственная уверенная цель; неоднозначность маскируется |
| 1 | `person_bearing` | Угол, делённый на половину горизонтального FOV; от −1 до 1 |
| 2 | `person_proximity` | `clip(1 - distance_m / depth_scale_m, 0, 1)` |
| 3–5 | `clearance_left/center/right` | `clip(clearance_m / depth_scale_m, 0, 1)` |

Неизвестное расстояние имеет `aux_mask=false` и ноль как заполнитель. Этот ноль не является подтверждением нулевого либо большого свободного пути. На runtime разрешение движения определяется отдельной проверкой метрического наблюдения и footprint, а не тремя предсказанными world model числами.

До завершения калибровки можно явно добавить `--allow-uncalibrated-pseudo` для исследовательской разметки. Такие данные помечаются как pseudo-labels, а не измеренная истина. Текущий флаг происхождения хранится в metadata и переносится в checkpoint. История калибровки и SHA256 файла исправления сохраняются для воспроизводимости. Полная новая разметка принятой калибровкой заменяет текущие признаки; старые записи остаются в истории.

Ручное исправление кадра:

```json
{
  "frames": {
    "17": {
      "person_visible": false,
      "clearance_m": [0.9, 0.35, 1.1],
      "clearance_valid": [true, true, false]
    }
  }
}
```

```bash
python -m room_world_model.label data/labeled/episode.npz \
  --output data/corrected/episode.npz \
  --manual-only --corrections measurements/corrections.json
```

Числа ручной коррекции тоже должны быть измерены или сознательно помечены как неизвестные. Можно вместо метрических полей задать `aux` из шести значений и обязательную `aux_mask` из шести boolean. Частичная ручная коррекция не меняет единицы нормировки остальных кадров и не даёт разрешения приводу.

## 8. Проверка первой задачи «подъедь к человеку»

### Проверка сохранённого кадра без ROS и привода

До запуска робота можно разобрать обычный исходный RGB JPEG из `sessions`:

```bash
python -m room_world_model.vision_check \
  --config config/robot.yaml \
  --image sessions/room_day1_layout_a/EPISODE_ID/rgb/CAMERA_EPOCH_000000001.jpg \
  --output measurements/vision_check.json
```

Путь изображения замените реальным файлом из своей сессии. Разрешение должно совпадать с `camera.json`; автоматического увеличения grayscale 128 × 128 здесь нет. Веса должны быть подготовлены заранее тем же загрузчиком, что для PC runtime. Утилита применяет заданный `intrinsics_file`, проверяет соответствие исправленной матрицы `camera.json` и передаёт маску краёв в perception. При принятой калибровке отсутствие исправления требует того же явного `already_rectified=true`, что и runtime; сам отчёт это значение не меняет.

JSON содержит обнаружение человека, расстояние и его valid-флаг, состояние `camera_calibration.accepted`, а также три отдельных кандидата: прямо, левая и правая дуга. Для каждого показаны фактические скорости после округления PWM, `required_clearance_pc_m`, `clearance_m`, `covers_swept_footprint`, `metric_valid` и `path_reason`. Вычисления вызывает `ControlEngine` в `shadow/teleop`: формула остановки и запрос полного пути те же, что на ПК. Отклонённая левая дуга не подменяется прямым путём в отчёте. `covers_swept_footprint=false` означает, что необходимое для этой дуги пространство не подтверждено наблюдением; большой clearance в центре не устраняет этот отказ.

Для трёх кандидатов выполняются три отдельных инференса. Поле `timing.budget_exceeded` сравнивает декодирование изображения и вычисление с `max_inference_s`; первый проход может быть медленнее из-за прогрева. Загрузка моделей приведена отдельно. Очередь ROS, передача сообщения, возраст экспозиции и задержка привода в таком тесте не измеряются. Даже быстрый проход не подтверждает полный runtime deadline.

Верхнеуровневые `accepted=false`, `motor_enable_allowed=false` и `freshness_evidence_available=false` присутствуют всегда: файл не доказывает текущую свежесть кадра или остановку робота. Утилита ничего не публикует, не открывает последовательный порт и не меняет флаги конфигурации. При неверной калибровке, отсутствующих весах или ошибке изображения она сохраняет JSON с `status=error` и возвращает ненулевой код завершения. Это позволяет сначала выяснить причину «не едет» по наблюдению и геометрии.

### Первая задача под наблюдением оператора

Начинайте с неподвижного взрослого участника, который видит робота, с большим свободным пространством и оператором рядом. Начальный standoff в проекте — 1 метр от модели центра робота до ближайшей оценки видимой части человека. Он не равен расстоянию от переднего бампера. Если человек уже ближе цели, робот остаётся на месте; отъезд назад фронтальной камерой не разрешается.

Порядок проверки: сначала обнаружение и дистанция без привода, затем принятие/отклонение предлагаемого пути в shadow mode, затем контролируемые короткие импульсы после отдельных измерений привода. Проверяйте, что потеря цели и появление второй цели прекращают задачу, а поздний результат старого кадра не порождает следующий импульс.

Переставленный предмет должен влиять на следующее наблюдение и новую проверку пути. Старое предсказание world model не имеет права отменять свежую неизвестность. Если предмет переместился в слепую зону уже после наблюдения, одной старой камеры недостаточно для надёжного обнаружения: именно поэтому длительность импульса, дистанция до людей, независимое прекращение PWM и следующий кадр после остановки являются частью эксперимента.

Полноценный обход возможен только по видимым дугам с покрытым footprint. Если такого пути нет, корректное действие этой версии — остановиться. Поворот на месте для поиска человека, самостоятельный задний ход, поиск человека в другой комнате и выбор конкретного человека по имени в эту реализацию не входят.

## 9. Переход с v1 и пределы готовности

Архив v2 содержит программную реализацию временных контрактов и инструменты измерения. В нём нет полученной на вашем роботе оптической калибровки, датасета, обученного на этой комнате checkpoint или аппаратного сертификата безопасности. Тестовые картинки, fake GPIO/MCU и проверки Python-адаптеров не являются такими измерениями.

V1-логи с временем OpenCV read и host-оценками импульса нельзя сделать подтверждёнными v2-данными заменой `schema_version`. Аудит старого NPZ:

```bash
python -m room_world_model.data --audit-v1 data/legacy_episode.npz
```

Команда помогает исследовать существующий файл; она не дорисовывает START/STOP и exposure bounds. Для обучения v2 динамики требуется новая запись с полным происхождением. Проверенный synthetic pipeline полезен для проверки shapes, loss и последовательности команд, но не даёт автоматического live acceptance.

Даже принятые timing и metric-depth границы не гарантируют, что одна фронтальная камера увидит новое препятствие сбоку, стекло, провод или человека, вошедшего после экспозиции. Для первого физического режима сохраняются оператор, ограниченные импульсы, самостоятельное прекращение PWM на MCU, проверка новой площади корпуса и новый кадр после остановки. World model ранжирует допустимые варианты и не отменяет свежую геометрическую неизвестность.
