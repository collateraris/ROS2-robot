# Неделя 3. Локальный LLM/VLM: команда → проверенный план → Nav2

Цель недели — выполнить понятную составную команду через уже проверенные
LiDAR, RF2O, карту и Nav2. Пример: «подъедь к стулу; подожди 2 секунды;
домой». Здесь модель выбирает **известные символические цели**, а геометрию,
маршрут и движение проверяет обычный код.

Две реализации решают одну задачу через один исполнитель:

| Backend | Что работает | Для чего сравнивать |
|---|---|---|
| `rules` | Детерминированная грамматика и зарегистрированные ID | Дешёвый воспроизводимый baseline |
| `ollama` | Настоящий локальный `/api/chat`, `qwen2.5vl:7b`, JSON schema | Более свободные формулировки, композиция задач; опционально изображение |

LangChain не требуется: `room_planning/backends.py` делает один HTTP-запрос
стандартной библиотекой Python. Здесь нет имитации ответа модели. Для реального
backend нужно отдельно установить и запустить Ollama и скачать его веса.

## 1. Что должно работать до этой недели

1. `ROS 2 Jazzy`, C1 `/scan`, RF2O, guard `/odom`, `/room_base/odom_healthy`.
2. Карта `/map`, действующий TF `map → odom → base_link → laser`.
3. Навигация к операторской цели Nav2 с проверенными приводом и остановкой.
4. Восприятие недели 2, выдающее **измеренные** объекты в `/room_semantics/objects`.

Для именованных точек достаточно карты и собственного YAML: детектор объектов
для `goto_waypoint` не требуется. Для `goto_object` нужен свежий доверенный
результат камеры + LiDAR; одна картинка или ответ VLM этого не заменяют.

Запускайте навигационную основу с **`start_mission:=false`**. Старый
`room_mission` и новый `room_tasks` — два клиента Nav2; одновременно принимать
команды на одном роботе они не должны. Дополнительный старый `person_goal`
тоже не запускайте параллельно с этим координатором.

Для продолжения симуляции недели 1 запустите основу в отдельном терминале:

```bash
source scripts/env_robot.sh
ros2 launch room_sim sim.launch.py start_mission:=false
```

Команды `room_tasks` ниже рассчитаны на эту симуляцию: `use_sim_time:=true`,
`robot_radius_m:=0.19`, `standoff_m:=1.0`. Они должны использовать те же `/clock`
и геометрию, что SLAM/Nav2. Не запускайте вторую копию основы, если она уже работает.

Для настоящего робота вместо симулятора используйте аппаратный запуск:

```bash
source scripts/env_robot.sh
ros2 launch room_nav bringup.launch.py \
  mode:=localization map:="$PWD/maps/room.yaml" \
  start_mission:=false \
  lidar_port:=/dev/serial/by-id/REPLACE_WITH_C1 \
  base_config:="$PWD/config/robot_base.yaml" \
  robot_radius:=0.18 laser_x:=0.0 laser_y:=0.0 laser_z:=0.15
```

Пути, радиус и положение LiDAR в аппаратной команде — пример. Подставьте свои
измерения. В командах `room_tasks` ниже для настоящего робота замените
`use_sim_time:=true` на `use_sim_time:=false` и укажите измеренный
`robot_radius_m`, а также выбранную дистанцию `standoff_m`. Реальный C1 и
Arduino в симуляции не запускаются.

`source scripts/env_robot.sh` нужен в каждом терминале: он добавляет корень
проекта в `PYTHONPATH`, чтобы установленный ROS console script видел
`room_planning`. Если запускаете вручную без этого скрипта, явно экспортируйте
`PYTHONPATH="$PWD:${PYTHONPATH:-}"` из корня проекта и подключите оба ROS setup.

## 2. Сначала rules в режиме наблюдения

```bash
source scripts/env_robot.sh
ros2 launch room_tasks tasks.launch.py backend:=rules \
  use_sim_time:=true robot_radius_m:=0.19 standoff_m:=1.0
```

По умолчанию `shadow_only=true`, `enable_execution=false`. В этом режиме
координатор проверяет и публикует план, но **не отправляет даже запросы пути
или навигационные цели**. Отдельная явная команда «стоп» всегда остаётся
действующей командой остановки.

В другом терминале:

```bash
source scripts/env_robot.sh
ros2 topic echo /room_semantics/objects
ros2 topic pub --once /room_tasks/command std_msgs/msg/String \
  '{data: "подъедь к стулу; подожди 2 секунды"}'
ros2 topic echo /room_tasks/plan
ros2 topic echo /room_tasks/events
```

Если в сцене ровно один подходящий стул, ожидается план вида:

```json
{"steps":[{"action":"goto_object","object_id":"chair_0001"},{"action":"wait","seconds":2.0}]}
```

`chair_0001` здесь — иллюстрация: настоящее имя берётся из текущего сообщения
восприятия. При двух людях «к человеку» отвергается. Можно явно выбрать
наблюдаемый ID, например «к person_0004». Это не режим автоматической слежки.

Грамматика `rules`: разделители `;`, `,`, «потом», «затем», `then`; операции
«к …», «подъедь к …», `go to …`, «подожди N секунд», «домой», «стоп».
Поддерживаются канонические классы `person/chair/table/door` и русские
названия. Неизвестная формулировка отвергается. Это намеренно ограниченный
baseline, с которым сравнивают модель, а не языковая нейросеть.

## 3. Именованные точки

Используйте собственный YAML с измеренными координатами именно текущей карты:

```yaml
frame_id: map
waypoints:
  home:
    pose: [0.50, 0.50, 0.0]
  desk:
    pose: [1.50, 0.80, 1.57]
```

Числа выдуманы для показа формата. Здесь должна быть свободная точка стоянки
рядом с предметом, а не центр самого стола. До замены чисел не включайте этот
файл. В отличие от старого `room_mission`, данный rules backend использует
**точные ключи** YAML (`home`, `desk`), не его поле `aliases`. Например:
«поезжай к desk», «домой».

```bash
ros2 launch room_tasks tasks.launch.py backend:=rules \
  use_sim_time:=true robot_radius_m:=0.19 standoff_m:=1.0 \
  waypoints_file:="$PWD/config/waypoints.yaml" waypoints_confirmed:=true
```

Без `waypoints_confirmed:=true` список разрешённых именованных точек пуст.
LLM не может добавить имя или координаты в этот список. Веса модели и карта
не содержат заранее знания вашей комнаты.

## 4. Настоящий локальный LLM/VLM через Ollama

На ПК установите Ollama по официальной инструкции для своей ОС, запустите
службу и скачайте модель:

```bash
ollama pull qwen2.5vl:7b
ollama list
```

Если служба ещё не работает, запустите `ollama serve` в отдельном терминале;
вторую копию при уже занятом порте запускать не нужно. Первый запрос может
загружать веса. Предварительный пробный запрос:

```bash
ollama run qwen2.5vl:7b "Ответь одним словом: готов"
```

Скорость зависит от GPU, памяти и размера входа. Координатор даёт inference
30 секунд, HTTP по умолчанию — 25 секунд. Если устройство не успевает,
задача завершается отказом; оно не получает разрешения ехать со старой целью.
После предварительной загрузки измерьте фактическое время у себя.

Сначала режим text + наблюдаемые ID, без изображения:

```bash
source scripts/env_robot.sh
ros2 launch room_tasks tasks.launch.py backend:=ollama model:=qwen2.5vl:7b \
  use_sim_time:=true robot_radius_m:=0.19 standoff_m:=1.0
```

Модель получает текст команды, список `{id,label,score}` текущих измеренных
объектов и разрешённые имена точек. **Координаты для генерации ей не нужны.**
В `/api/chat` передаётся `format` с JSON schema и enum существующих ID.
После ответа независимый Python parser снова проверяет результат.

Для варианта VLM добавьте `use_image:=true`; нужен свежий raw Image на
`/camera/image_raw` (rgb8/bgr8/rgba8/bgra8/mono8):

```bash
ros2 launch room_tasks tasks.launch.py backend:=ollama \
  use_sim_time:=true robot_radius_m:=0.19 standoff_m:=1.0 \
  model:=qwen2.5vl:7b use_image:=true
```

Картинка уменьшается до не более 640×480 и отправляется локальной модели
как JPEG в base64. Изображение даёт контекст, но не разрешает модели придумать
новый ID, расстояние или моторное действие. Если VLM «увидела» человека,
которого нет в доверенном метрическом списке, она не может послать робота к нему.

Endpoint разрешён только loopback HTTP (`127.0.0.1`, `localhost`, `::1`).
Запускайте этот узел на том же ПК, где Ollama. Общение с Raspberry Pi в такой
схеме идёт через ROS, а не через публичный сервер модели.

Официальные источники: [Ollama chat API](https://docs.ollama.com/api/chat),
[structured outputs](https://docs.ollama.com/capabilities/structured-outputs),
[Qwen2.5-VL в Ollama](https://ollama.com/library/qwen2.5vl).

## 5. Разрешение выполнения

После проверки планов в shadow остановите только узел задач и перезапустите:

```bash
source scripts/env_robot.sh
ros2 launch room_tasks tasks.launch.py backend:=rules \
  shadow_only:=false enable_execution:=true \
  use_sim_time:=true robot_radius_m:=0.19 standoff_m:=1.0 \
  waypoints_file:="$PWD/config/waypoints.yaml" waypoints_confirmed:=true
```

Для реальной модели замените `backend:=rules` на `backend:=ollama`. Радиус
должен совпадать с измеренной охватывающей геометрией Nav2. Независимые
`allow_actuation`, `calibration_confirmed`, ARM и deadman привода остаются
обязательными. Координатор не вызывает ARM и не публикует `/cmd_vel`.

Запустите окно задач:

```bash
python -m robot_extras.task_operator
```

Порядок: заранее ввести задачу → отправить → дождаться события
`goal/navigation_requested` или `step/navigating` → удержать зелёную кнопку
и нажать A. Загрузка модели может занять время: преждевременный ARM не
создаёт длинную сессию без команд. Удерживайте deadman на протяжении движения.
Отпускание и потеря сенсоров прекращают поездку. Прежний ARM не восстанавливается
автоматически; после прерванной задачи отправьте новую явную команду.

В симуляции автоматический ARM допустим только через отдельный явно включённый
симуляционный адаптер/runner из недели 4. На настоящем роботе этого режима нет.

Для каждого движения код делает следующее:

1. Проверяет `/map`, свежую лазерную одометрию и TF положения робота.
2. Для объекта заново находит тот же ID, проверяет возраст, score и
   `uncertainty_m ≤ 0.3 м`. Сопоставляет с позой, известной до inference.
3. Строит точку на расстоянии `standoff_m=0.8 м` со стороны робота,
   разворачивает робота к измеренному объекту. Координаты создаёт код.
4. Требует свободные клетки под целым кругом корпуса + запасом 0.05 м.
   Выход за карту, неизвестные клетки и препятствия — отказ.
5. Запрашивает `ComputePathToPose`. Требует успешный конечный путь в `map`
   с правильными началом/концом. Дополнительно проверяет круг корпуса вдоль
   каждого отрезка пути с шагом не больше половины клетки карты: неизвестные
   и занятые клетки между редкими точками тоже дают отказ. Объём ограничен
   100 000 проверками. Лишь затем разрешается `NavigateToPose`.
6. Ещё раз проверяет цель после расчёта пути, затем постоянно во время движения.

Если цель пропала, устарела или сдвинулась более чем на 0.3 м, действие
отменяется и защёлкивается остановка. Автоматической погони за человеком нет.
Если при повороте человек надолго вышел из камеры, это тоже отказ; текущая
система не заявляет надёжную память о невидимых динамических объектах.

При медленном inference исходному snapshot может быть 20 секунд, но результат
принимается только если тот же ID всё ещё **свежо** наблюдается и не сдвинулся
за это время. Старая исходная поза не подменяет новую сцену.

## 6. Остановка, отмена и повторный запуск

```bash
ros2 topic pub --once /room_tasks/command std_msgs/msg/String '{data: "стоп"}'
```

STOP обрабатывается сразу, без вызова модели. Узел защёлкивает
`/room_base/estop`, отменяет path/navigation actions и меняет generation token.
Поздний ответ модели или поздно принятая цель старой задачи не могут продолжить
движение. Новый текст во время задачи отменяет предыдущую; автоматического
повторного разрешения привода нет.

После физической остановки и устранения причины:

```bash
ros2 service call /room_base/reset_estop std_srvs/srv/Trigger '{}'
```

Робот остаётся disarmed. Задайте новую задачу, дождитесь навигационной цели,
затем отдельно удерживайте deadman и запросите ARM. Старые команды не
кэшируются мостом для следующей ARM-сессии. `estop=false` защёлку не снимает.

## 7. Какие действия допускаются

```json
{"steps":[
  {"action":"goto_object","object_id":"chair_0001"},
  {"action":"wait","seconds":2.0},
  {"action":"goto_waypoint","name":"home"},
  {"action":"stop"}
]}
```

До 8 шагов; одно ожидание 0–10 секунд, сумма ожиданий до 30 секунд;
`stop` только последним шагом. Неизвестные поля, дубли JSON-ключей, NaN,
координаты, скорости, произвольные действия и неизвестные ID отвергаются.
Модель не имеет shell, инструментов или произвольного доступа к ROS.

`stop` в валидном плане — конечная остановка; если Ollama не смогла понять
запрос и вернула только stop, робот остановится. Такой результат не означает,
что исходная задача «к столу» выполнена правильно. Для оценки смотрите план и
внешний критерий успеха недели 4, не только статус завершения плана.

## 8. Интерфейсы и логи

| Имя | Данные |
|---|---|
| `/room_tasks/command` | String: обычный текст либо JSON `{request_id,instruction}` |
| `/room_semantics/objects` | Доверенная метрическая сцена v1; результат недели 2 |
| `/room_tasks/plan` | String JSON: проверенный план и длительность inference |
| `/room_tasks/events` | JSON: запрос, план, цель, шаг, итог |
| `/room_nav/demo_context` | Только принятая Nav2-задача `{instruction,target,generation}` для recorder |
| `/compute_path_to_pose`, `/navigate_to_pose` | Nav2 actions |
| `/room_base/estop` | Защёлкиваемая остановка; привод принадлежит отдельному узлу |

Пример коррелированной команды для эксперимента:

```bash
ros2 topic pub --once /room_tasks/command std_msgs/msg/String \
  '{data: "{\"request_id\":\"trial-001\",\"instruction\":\"домой\"}"}'
```

События имеют поля `schema_version=1, stamp_ns, request_id, generation,
event, status, details`. Конечное событие — `event=task_result`; status:
`succeeded`, `rejected`, `canceled`, `failed` или `shadow`. Полный журнал
по умолчанию `logs/week03_tasks.jsonl`; путь меняется через YAML `log_file`.
Записываются команды/планы/метрические цели/результаты, но не изображения,
полные HTTP-ответы, окружение или секреты.

Параметры считываются при старте: редактируйте свой YAML и перезапускайте
узел с `config:=/absolute/path/tasks.yaml`. Launch-параметры `backend`,
`shadow_only`, `enable_execution`, `use_image`, `waypoints_file`,
`waypoints_confirmed`, `robot_radius_m`, `standoff_m`, `use_sim_time` явно перекрывают YAML;
передавайте их в launch-команде.

## 9. Что находится в коде

| Файл | Назначение |
|---|---|
| `room_planning/core.py` | Строгие схемы, freshness, disambiguation, geofence, standoff, cancellation token |
| `room_planning/backends.py` | Rules и реальный локальный Ollama chat с JSON schema |
| `ros2_ws/src/room_tasks/room_tasks/coordinator.py` | ROS callback/action state machine, inference worker, STOP, журнал |
| `ros2_ws/src/room_tasks/config/tasks.yaml` | Консервативные настройки по умолчанию |
| `ros2_ws/src/room_tasks/launch/tasks.launch.py` | Запуск /room_tasks |
| `tests/test_planning_*.py` | Парсинг, геометрия, async STOP, shadow, модельный API с заглушкой транспорта |

Inference работает в отдельном worker, а ROS callbacks продолжают принимать
STOP и сцену. Число одновременно живых запросов ограничено двумя. Generation
token аннулирует старые ответы/goal handles. Путь и движение имеют собственные
таймауты; по ошибке задача не возобновляется автоматически.

## 10. Связь с VLA и world model

Qwen2.5-VL здесь — pretrained VLM верхнего уровня: по языку/картинке выбирает
символические действия. Точные моторные действия выполняют Nav2 и привод.
Готового pretrained VLA для точного управления именно вашим шасси здесь нет.
Камера + 2D LiDAR дают плоскую опору цели, а не полноценную 3D-модель предмета.

Унаследованные `learning_nav/TinyVLA` и `WorldModel` — отдельные небольшие
модели, обучаемые с нуля на ваших данных. Они не становятся pretrained VLA от
подключения Qwen и не входят в моторный контур. `demo_context` публикуется лишь
после принятия NavigateToPose: именованная цель может дать класс из metadata,
объектный ID без класса даст label=-1. Разбор/оценка этих данных — в
`docs/LEARNING_RU.md`.

## 11. Проверка и критерий завершения недели

```bash
python -m pytest -q tests/test_planning_core.py \
  tests/test_planning_backends.py tests/test_planning_coordinator.py
```

Offline-тесты проверяют строгий parser, отбрасывание выдуманных координат,
неоднозначных/старых/сдвинутых объектов, границы и поворот карты, неизвестные
клетки, геометрию пути, STOP во время inference/позднего принятия цели,
неисполнение shadow и отсутствие автоматического продолжения после потери odom.
В тесте HTTP заменён транспорт: это проверка реального формата API-кода,
**не запуск весов Qwen и не доказательство качества модели**.

Завершение недели: несколько задач rules и Ollama в одной и той же комнате,
с сохранёнными JSONL и внешней проверкой, что достигнут именно нужный объект;
успешные испытания STOP, пропажи объекта и перемещения человека. ROS action
совместимость, модель, восприятие и движение нужно проверить на целевой системе.
Без этих испытаний код остаётся подготовленной реализацией, не проверенной
на вашем роботе автономностью.
