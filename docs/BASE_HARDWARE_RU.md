# Привод без энкодеров: прошивка, PWM и калибровка v5

## Что изменилось

Активная прошивка: `firmware/room_base_rf2o/room_base_rf2o.ino`, USB serial 115200, протокол **V5 signed PWM**. Энкодеров, энкодерного PI и моторной одометрии в ней нет. Моторы работают непрерывно до следующей команды/STOP/watchdog. Старые Bluetooth-импульсы v2 и скоростной протокол V4 из v3 несовместимы с новым мостом.

RF2O через guard даёт `/odom`. Мост принимает номинальную скорость Nav2 и переводит её в PWM по отдельным калибровкам левого/правого мотора вперёд/назад. `/room_base/applied_cmd_vel` — **подтверждённая MCU номинальная уставка**, не измеренная скорость.

## Плата и пример распиновки

Прошивка рассчитана на **Arduino Uno / classic Nano ATmega328P** и две управляемые стороны дифференциального привода через двухканальный H-мост. Для Mega/ESP32/Nano Every или другого моторного драйвера нужно адаптировать низкоуровневый код. Наличие двух или четырёх физических моторов само по себе не определяет допустимое подключение: токи драйвера и объединение по сторонам проверить по конкретному устройству.

| Назначение | Пин примера |
|---|---|
| Левый мотор, направление L1/L2 | D3 / D2 |
| Правый мотор, направление R1/R2 | D4 / D5 |
| Левый PWM/ENA | D9 |
| Правый PWM/ENB | D6 |
| Serial USB | D0/D1 через USB-UART |
| Энкодеры | Не используются |

Пример сохраняет моторные пины legacy_v2; он не заменяет проверку схемы твоего робота. `LEFT_MOTOR_SIGN` и `RIGHT_MOTOR_SIGN` в примере равны `-1`, их нужно сверить при поднятых колёсах. PWM ограничен `MAX_PWM=120`; не повышать лимит для обхода отсутствующей калибровки. Timer2 занят watchdog; D3 здесь — обычное направление, не PWM.

В legacy был `A0=HIGH` с неизвестным назначением. В новой прошивке `DRIVER_ENABLE_PIN=-1`. Если **по схеме твоего драйвера** A0 действительно включает его высоким уровнем, выставить `DRIVER_ENABLE_PIN=A0`. Подтяжки ENA/ENB вниз и отключение питания привода должны удерживать моторы выключенными при reset/загрузке Arduino. Нулевой PWM снимает тягу, но не гарантирует мгновенного механического торможения.

## Сначала тест направления

Установить Arduino IDE по [официальной инструкции](https://docs.arduino.cc/software/ide-v2/tutorials/getting-started/ide-v2-uploading-a-sketch/).
Открыть `firmware/room_base_rf2o/room_base_rf2o.ino`, выбрать в Boards Manager пакет **Arduino AVR Boards**,
свою плату Uno либо classic Nano и фактический USB-порт. Для Nano выбрать соответствующий реальному
загрузчику Processor; варианты ATmega328P и Old Bootloader не взаимозаменяемы при загрузке.
Сначала Verify, затем Upload с отключённым питанием моторов. Закрыть Serial Monitor перед запуском
ROS-моста или калибратора: serial должен иметь одного владельца. Внешние Arduino-библиотеки не требуются.
Host-тесты проекта не являются AVR-компиляцией этой прошивки.

Во всех терминалах ROS/Python из корня проекта сначала `source scripts/env_robot.sh`.

1. Отключить питание моторов, сверить пины, загрузить новую прошивку под Uno/classic Nano. Поднять и закрепить колёса, освободить пространство вокруг них.
2. Нормальный мост **не должен владеть serial**: использовать `start_bridge:=false` либо остановить его процесс. Не запускай одновременно v2, encoder bridge, новую базу и инструмент калибровки на одной Arduino.
3. В отдельном терминале из корня проекта выполнить **одну** короткую пробу:

```bash
python -m robot_extras.pwm_calibrate \
  --port /dev/serial/by-id/REPLACE_ARDUINO_ID \
  --left-pwm 60 --right-pwm 0 --seconds 0.3 \
  --raised-wheels --confirm-bench-test
```

Здесь положительный PWM должен означать движение левой стороны вперёд. Проверить правую сторону отдельным запуском, затем отрицательные PWM. Режим `--raised-wheels` только для проверки знаков: он ограничен |PWM|≤80 и длительностью≤0.5 с, не измеряет скорость движения робота и не требует ROS сенсоров. Ctrl-C прекращает тест; программный STOP и MCU watchdog не заменяют физическое отключение питания.

## Калибровка на полу

Сначала запустить mapping с `start_bridge:=false`, C1 и guard. Убедиться, что `/room_base/odom_healthy=true`, `/odom` соответствует реальному медленному ручному перемещению. Затем использовать инструмент без `--raised-wheels`:

```bash
python -m robot_extras.pwm_calibrate \
  --port /dev/serial/by-id/REPLACE_ARDUINO_ID \
  --left-pwm 60 --right-pwm 60 --seconds 0.5 \
  --confirm-bench-test
```

Это **один ограниченный ручной тест**, а не автономная поездка: он намеренно подаёт указанный PWM без Nav2/Collision Monitor. Оператор обеспечивает свободный участок и готовность снять питание. Floor-режим требует свежие `/scan`, `/odom` и health, предел |PWM|≤120, длительность≤1 с; при отказе/таймауте останавливается, автоматически движение не повторяет. Возможности остановки ближе к препятствию через Nav2 здесь не используются.

Для каждой стороны/направления определить:

- `*_min_pwm`: минимальный PWM, при котором колесо устойчиво вращается **под реальной нагрузкой**, а не только на поднятом шасси.
- `*_min_mm_s`: соответствующая минимальная непрерывная скорость.
- `*_max_pwm` и `*_max_mm_s`: выбранная верхняя точка в пределах MCU MAX_PWM и умеренной скорости.

Короткие пробы дают первоначальную оценку. Можно считать обороты отмеченного колеса по видео: `скорость=π×диаметр×обороты/время`. Проверка прямого перемещения по рулетке и времени нужна для контроля результата на полу. Скорость из RF2O — полезная дополнительная оценка; на малых сантиметровых перемещениях она шумная и не является независимой точной калибровкой. Не выдавай предполагаемые числа за измеренные.

Четыре линейных участка `SpeedCurve` в `base.yaml` задают различие сторон и направлений. Если зависимость существенно нелинейная, улучшить таблицу/интерполяцию либо уменьшить рабочий диапазон. Заряд батареи, покрытие и нагрузка меняют открытый контур; проверять поведение после их изменения.

## Конфигурация и первый Nav2 запуск

Создать собственную копию конфигурации:

```bash
mkdir -p config
cp ros2_ws/src/room_base/config/base.yaml config/robot_base.yaml
```

В `config/robot_base.yaml` записать реальный serial-порт, `wheel_separation_m` и четыре калибровки. Колея — расстояние между центрами пятен контакта левой/правой сторон. Диаметр нужен для ручного измерения скорости, но не для расчёта RF2O-позы.

После проверки заполненных значений установить:

```yaml
allow_actuation: true
calibration_confirmed: true
```

Это локальные признаки готовности hardware-конфигурации. ARM по-прежнему выдаётся только отдельным запросом оператора. Передать YAML через `base_config:="$PWD/config/robot_base.yaml"`; так используется своя копия без зависимости от пересборки installed-конфига.

Согласовать Nav2 с минимальной скоростью: для вращения на месте нужна `|omega| >= 2×min_wheel_speed/track`. Пример 20 мм/с и колея 0.16 м даёт 0.25 рад/с. Дефолтные лимиты Nav2 0.10 м/с и 0.40 рад/с подходят **только примерной калибровке**. Если твой мотор требует большей минимальной скорости, slow zone/малые угловые команды могут превратиться в STOP; нельзя исправлять это скрытым увеличением PWM на микрокоманде. Настроить минимальные скорости/допуски достижения цели либо поменять привод.

Сначала проверить остановку при отпускании deadman, STOP, отключении LiDAR и serial, затем короткую прямую поездку и поворот в свободной зоне. После этого разрешать цели RViz. Тормозные зоны и radius задавать по всему корпусу и измеренному торможению.

## ROS-интерфейсы

| Имя | Тип/смысл |
|---|---|
| `/cmd_vel_safe` | Twist: номинальная скорость после Collision Monitor |
| `/scan`, `/odom` | Свежие лазерные данные и guarded RF2O |
| `/room_base/odom_healthy` | Bool от guard; отсутствие/false запрещает привод |
| `/room_base/deadman` | Bool, удерживаемое разрешение оператора, heartbeat 20 Гц |
| `/room_base/arm` | Trigger: новая сессия, подтверждение в `/armed` |
| `/room_base/stop` | Trigger: STOP, снятие ARM |
| `/room_base/estop` | Bool true: защёлкнуть запрет; false его не снимает |
| `/room_base/reset_estop` | Trigger: сброс только в остановленном состоянии, без ARM |
| `/room_base/armed`, `/room_base/status` | Состояние моста и причина отказа |
| `/room_base/applied_cmd`, `/room_base/applied_cmd_vel` | TwistStamped: ACK-accepted номинальная уставка |

Свежесть контролируется и по исходным временным меткам, и по локальному приёму. MCU имеет командный watchdog 250 мс, контроль main loop 50 мс и аппаратный AVR watchdog. CRC, session и sequence защищают от повреждённых/повторённых команд; это не сертификат безопасности и не подтверждение физического торможения.
