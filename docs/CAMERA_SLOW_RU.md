# Камера открылась, но read занимает 0.5–3 секунды

Эта инструкция относится к USB UVC-камере `/dev/video0`, Ubuntu 24.04 arm64, ROS 2 Jazzy и проекту `robot_wifi_teleop`. В предоставленном диагностическом логе OpenCV 4.6.0 успешно вернул все 10 кадров MJPG 640×480: первый за 2.877 с, остальные за 0.567–0.752 с. Это примерно 1.3–1.8 кадра/с после первого чтения, а не заявленные в свойствах драйвера 30 fps.

## Почему старый узел переподключался

В предыдущем `camera_node.py` и неудачное чтение, и успешное чтение дольше `max(0.5, 2/fps)` секунды приводили к одной ошибке `Camera read failed or stalled; reconnecting`. При обычном `fps=15.0` порог равен 0.5 секунды. Поэтому узел отбрасывал первый успешный кадр и снова открывал устройство; даже после прогрева все последующие кадры из приведённого лога тоже превышают этот порог.

Это ошибка реакции узла на медленный поток. Она не устанавливает причину медленной работы самой камеры. `cap.set(...)=True` не гарантирует, что камера приняла именно запрошенное значение; `cap.get(CAP_PROP_FPS)` сообщает свойство режима, а не измеряет, сколько кадров получено приложением за секунду. См. [OpenCV 4.6 VideoCapture](https://docs.opencv.org/4.6.0/d8/dfe/classcv_1_1VideoCapture.html) и [V4L2 streaming parameters](https://docs.kernel.org/userspace-api/media/v4l/vidioc-g-parm.html).

## Что исправлено

- Успешное медленное чтение сохраняет открытое устройство. В журнале отдельно сообщается его длительность. Неудачное чтение, пустой или некорректный кадр по-прежнему приводят к повторному открытию.
- Обычные `camera/image_raw` и `camera/image_raw/compressed` получают кадр только после прохождения прежней проверки длительности. Медленный успешный кадр очищает обычный кеш и не получает новую метку для обхода этой проверки.
- При `preview_enabled:=true` отдельная тема `camera/preview/compressed` получает также медленные валидные кадры. Каждый новый кадр публикуется однократно. Перед публикацией проверяется возраст до 0.5 с после чтения, в том числе после JPEG-кодирования. В заголовке остаётся время получения кадра на Pi, не аппаратное время экспозиции.
- Новый `camera_view.launch.py` запускает камеру и веб-сервер в режиме `view_only`. Такой сервер вообще не создаёт издателя команд движения и отвергает запросы включения управления. `motor_bridge` в этом launch отсутствует.
- Страница просмотра хранит последнее полученное изображение до 5 с по времени получения на Pi. Повторный HTTP-ответ с тем же токеном не считается новым кадром на странице. При прекращении кадров появляется надпись ожидания. Это диагностический просмотр, а не измерение задержки от съёмки до экрана.
- `pixel_format` камеры принимает `MJPG` или `YUYV`. Новый просмотр запрашивает 640×480, 30 fps: оба таких режима есть в предоставленном списке камеры. Обычная конфигурация робота остаётся с прежними значениями; изменения формата не выполняются установщиком.

Увеличения действительной частоты кадров это исправление не гарантирует. При текущих измерениях ожидается редкое обновление картинки.

## 1. Установить небольшое обновление

Скачайте `robot_camera_fix.zip` в Downloads на Windows. Распаковывать его в Windows не требуется.

**PowerShell Windows, не внутри SSH:**

```powershell
$piIp = Read-Host "IP Raspberry Pi, который используешь для SSH"
scp "$env:USERPROFILE\Downloads\robot_camera_fix.zip" "shapturov@${piIp}:~/"
```

Используйте реальный LAN-адрес Pi. `127.0.1.1` и `127.0.0.1` не обозначают удалённую Pi; `192.168.1.42` в прежних примерах также нужно заменять, если адрес устройства другой.

**SSH-терминал Raspberry Pi:** сначала остановите работающий launch и отдельные процессы камеры/веб-сервера через `Ctrl+C` в тех терминалах, где они запущены. Для запуска в `tmux` сначала выполните `tmux attach -t robot` и остановите launch там. Затем:

```bash
unzip -o ~/robot_camera_fix.zip -d ~/robot_camera_fix_update
python3 ~/robot_camera_fix_update/robot_camera_fix/install.py --project ~/robot_wifi_teleop
```

Установщик проверяет исходные файлы до записи, сохраняет изменяемые файлы в отдельную резервную папку и добавляет файлы просмотра. Если он сообщил о неизвестных локальных изменениях, остановитесь: не заменяйте такие файлы принудительно. Сохраните его вывод для согласования изменений. После успешной установки:

```bash
source /opt/ros/jazzy/setup.bash
cd ~/robot_wifi_teleop/ros2_ws
colcon build --symlink-install --packages-select robot_web_teleop
```

Продолжайте только после успешной сборки. Пересборка нужна для установки нового launch и HTML. Переустанавливать Ubuntu, ROS или перепрошивать Arduino для этого исправления не требуется. Если вы только что распаковали обновлённый полный архив, отдельный установщик исправления не нужен: достаточно собрать проект.

## 2. Открыть камеру в браузере

**SSH-терминал Pi:**

```bash
cd ~/robot_wifi_teleop
bash scripts/view_camera.sh camera_device:=/dev/video0
```

Скрипт запросит пароль минимум из 8 символов. При вводе пароль не отображается. Скрипт подключает установленную ROS-среду проекта, использует домен 42 и локальное обнаружение, если вы явно не задали другие значения. Оставьте команду работающей.

На компьютере или телефоне откройте `http://АДРЕС_PI:8080/`, заменив `АДРЕС_PI` адресом из SSH, и введите этот пароль. Дождитесь первого кадра: в предоставленном тесте само первое чтение заняло почти 3 секунды. Вы увидите отдельную страницу «Камера робота» без джойстика. В журнале ожидаются сообщения о выбранном формате и `VIEW ONLY`.

Предупреждение `slow successful read ... seconds, control frames withheld` сообщает о медленном кадре; в режиме просмотра такой кадр может отображаться. Это не прежняя ошибка переподключения. Если всё ещё написано `Camera read failed or stalled; reconnecting`, вероятно, работает старая версия или старый процесс: завершите прежний запуск и проверьте успешность обновления и сборки.

Для завершения нажмите `Ctrl+C`. Не запускайте одновременно `run_robot.sh`, отдельный `camera_node` и этот просмотр. Режим просмотра не останавливает посторонние программы управления; старый запуск нужно завершить самостоятельно.

## 3. Проверить причину низкой частоты

Сначала завершите просмотр (`Ctrl+C`). Все проверки ниже выполняются на Pi при свободной камере. Число 30 в сообщении о режиме не заменяет измерение получаемого потока.

### Доступные настройки

```bash
v4l2-ctl -d /dev/video0 --list-ctrls-menus
v4l2-ctl -d /dev/video0 --get-parm
```

Пока ничего не меняйте в экспозиции. Проверьте поведение при хорошем равномерном освещении. Автоэкспозиция с разрешённым изменением FPS может уменьшать частоту кадров; это возможная, но не доказанная причина данного случая. Стандартное поведение описано в [V4L2 Camera Control Reference](https://docs.kernel.org/userspace-api/media/v4l/ext-ctrls-camera.html). Присутствие и названия соответствующих controls сначала нужно увидеть в реальном выводе камеры.

### Захват MJPG без OpenCV

```bash
timeout --kill-after=2s 30s v4l2-ctl -d /dev/video0 \
  --set-fmt-video=width=640,height=480,pixelformat=MJPG \
  --set-parm=30 --stream-mmap=4 --stream-count=30 --stream-to=/dev/null
```

Команда получает до 30 кадров, записывает их в `/dev/null` и ограничена по времени. Сохраните её полный вывод, включая строки с измеренной частотой и возможные ошибки. Съёмка напрямую через V4L2 не декодирует JPEG средствами OpenCV. Возможности утилиты описаны в [v4l2-ctl manpage](https://manpages.debian.org/bookworm/v4l-utils/v4l2-ctl.1.en.html).

### Захват YUYV без OpenCV

После завершения предыдущей команды:

```bash
timeout --kill-after=2s 30s v4l2-ctl -d /dev/video0 \
  --set-fmt-video=width=640,height=480,pixelformat=YUYV \
  --set-parm=30 --stream-mmap=4 --stream-count=30 --stream-to=/dev/null
```

Оба режима уже присутствуют в предоставленном списке устройства. YUYV не гарантирует ускорения; сравнение помогает определить, на каком участке возникает задержка.

| Результат | Что исследовать дальше |
|---|---|
| Оба режима V4L2 медленные | Экспозицию и другие доступные настройки, USB-соединение, питание, драйвер и саму камеру |
| V4L2 MJPG быстрый, OpenCV MJPG медленный | Раздельные времена `grab()` и `retrieve()`, декодирование и настройки буферов; здесь V4L2 использует 4 буфера, исходный OpenCV-тест просил 1 |
| Только YUYV быстрый | Сравнить просмотр OpenCV с `pixel_format:=YUYV` |

Просмотр YUYV запускается той же командой с аргументом:

```bash
cd ~/robot_wifi_teleop
bash scripts/view_camera.sh camera_device:=/dev/video0 pixel_format:=YUYV
```

Если оба режима остаются медленными, проверьте прямое USB-подключение без хаба, исправный кабель/порт и питание Pi. Для следующего разбора полезны:

```bash
lsusb -t
sudo journalctl -k -b --no-pager -n 100
```

Нужно искать реальные сообщения о reset/disconnect, ошибках USB или питания. Название `MI1320_SOC` само по себе не доказывает неисправность камеры. Не меняйте драйвер и не переустанавливайте систему по одному этому названию.

## Ограничения проверки

Исправление проверяется программными тестами с подстановкой источника кадров, включая длительности из приведённого лога, и HTTP/WebSocket-тестами режима просмотра. Физическая камера и Raspberry Pi в среде разработки недоступны. Фактические FPS, запуск ROS на вашей Pi и отображение на вашем телефоне нужно подтвердить на устройстве.
