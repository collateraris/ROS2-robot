# Проверки и первый запуск

## Что проверено при подготовке

Проверки выполнены в Linux с Python 3.12.14. Использованы настоящий `aiohttp` HTTP/WebSocket-сервер, тестовые источники кадров и привода, а также C++-подстановка Arduino API. Это позволяет проверить программные переходы состояний без подключения моторов.

| Проверка | Результат | Практический предел |
|---|---|---|
| `unittest`: камера, режим просмотра, управление, протокол, мост, HTTP/WebSocket | **47 тестов прошли** | Ввод/вывод ROS и железа заменён в соответствующих тестах |
| Реальный `robot_drive.ino` внутри C++ harness | Скомпилирован и выполнен через `g++ -Wall -Wextra` | Host-сборка, не AVR и не измерение электрических сигналов |
| Python AST | 15 Python-файлов без синтаксических ошибок | Не проверяет загрузку настоящих ROS-библиотек |
| Shell | `bash -n` для скриптов и проверенных блоков инструкций | Установка пакетов ОС не выполнялась |
| Телефон | JavaScript прошёл `node --check`, DOM ID-ссылки согласованы | Реального браузера iOS/Android в среде не было |
| Пакет Python | Собран wheel, проверены 7 модулей, ROS-ресурсы и 3 точки входа | Не является проверкой `colcon` на Pi |

В тестах проверены: необходимость включения управления; отпускание; отсутствие команд; истечение challenge; чужой владелец; повторный и запоздалый arm; NaN/Inf и неверные диапазоны; последовательность пакетов; остановка при неисправности камеры или Arduino; рабочий WebSocket при переставшем обновляться подтверждении видео; logout и reconnect; повреждённые CRC и переполнение входа; boot lock; MCU watchdog; устаревший ACK; замена ожидающего ненулевого запроса нулём.

Для исправления медленной USB-камеры добавлены 18 тестов: успешные чтения длительностью 2.877, 0.567 и 0.752 с доступны только в preview и не переподключают камеру; следующее быстрое чтение возвращает обычную публикацию; пустой/ошибочный кадр вызывает reconnect; возраст повторно проверяется после JPEG-кодирования; кадры не повторяются с новой меткой. Проверены отдельная тема просмотра, TTL 5 с только для просмотра, сохранение обычного лимита 0.7 с в веб-сервере и отсутствие издателя `cmd_vel` в режиме `view_only`, даже после внешнего `ready=True`. HTTP/WebSocket-тест подтверждает доступность изображения и отказ включить движение в этом режиме. Исходные длительности взяты из пользовательского лога; физическая камера в тестах заменена.

**Не выполнялись:** запуск ROS 2 на Raspberry Pi, реальный USB-захват камеры, нативная компиляция для платы Arduino, загрузка прошивки, электрические и механические испытания, измерение задержки Wi-Fi и тормозного пути, отрисовка и касания в Safari/Chrome на телефоне. Значения частот и тайм-аутов в документации — настройки программы, не результаты измерения на вашем роботе.

## Как повторить программные тесты

В Ubuntu с установленным `python3-aiohttp` и `g++`, из корня распакованного проекта:

```bash
cd ~/robot_wifi_teleop
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Эти тесты запускаются без установленного ROS и без подключённого робота: аппаратные зависимости подменены. Проверка прошивки пропускается, если не найден `g++`; смотрите итог `skipped`, а не только слово OK. Полная инструкция установки зависимостей — INSTALL_RU.md.

## Первый тест с поднятыми колёсами

1. Проверьте маркировку драйвера, питание, общую землю, назначение пинов и аппаратное выключенное состояние входов разрешения во время reset. Моторное питание выключено при монтаже. Выключатель должен оставаться доступным.
2. В Arduino IDE выберите настоящую плату и порт, нажмите Verify, затем Upload. После загрузки закройте Serial Monitor и соедините Arduino USB с Pi. Uno R3 и классический Nano используют разные пункты Board; у некоторых Nano нужен вариант Old Bootloader.
3. Запустите ROS-проект по INSTALL_RU.md. До включения управления колёса должны оставаться неподвижными. В браузере должна появиться свежая картинка, признак связи и готовности Arduino.
4. Нажмите «Взять управление» без касания джойстика. Колёса по-прежнему неподвижны. Кратко отклоните джойстик вперёд, отпустите. Оба мотора одной стороны должны вращаться в одном физическом направлении. Проверьте назад, влево и вправо; меняйте полярность или знаки только при отключённом моторном питании.
5. Если моторы не стартуют на начальных 35%, не держите их под нагрузкой: проверьте питание/проводку и кратковременно увеличьте ползунок с поднятыми колёсами. Здесь 35% — доля команды пульта, не 35% от 255 PWM. Настройки смешивания могут дополнительно уменьшать PWM.
6. Во время небольшого вращения отпустите джойстик, нажмите СТОП, переключите вкладку, заблокируйте экран, затем отдельно отключите Wi-Fi телефона. В каждом случае движение должно прекратиться. После возврата оно должно оставаться выключенным до явного повторного включения.
7. Повторите тест, отключив USB-камеру. Канал команд может оставаться подключённым, но потеря свежего видео должна выключить управление. Вернув камеру, дождитесь свежего изображения; если драйвер захвата завис, завершите и снова запустите launch.
8. Проверьте потерю USB Arduino. В данном подключении Arduino питается через USB, поэтому такой тест одновременно отключает ей питание; это **не отдельное измерение watchdog MCU**. После возврата USB должен выполниться нулевой handshake и потребоваться новое включение управления.
9. Для отдельной проверки MCU watchdog при сохранённом USB-питании опытный оператор может приостановить **только процесс motor_bridge** сигналом SIGSTOP. В течение заданных 350 мс после последней валидной команды прошивка выбирает нулевой PWM. Верните процесс сигналом SIGCONT; старое движение не должно восстановиться. Делайте это исключительно на стенде, с точно определённым PID и поднятыми колёсами. Если этот тест незнаком, сначала отработайте предыдущие пункты и обычное завершение launch через Ctrl+C.
10. Войдите со второго браузера: второй пульт не должен перехватывать активное управление, но его СТОП должен сработать. После этого управление включается заново выбранным оператором.
11. Убедитесь, что выключатель моторного питания останавливает привод независимо от веб-страницы. Только после всех успешных проверок опустите робот в свободном месте и проведите короткую поездку на малой скорости под непосредственным наблюдением.

Программное обнуление PWM и фактическая остановка робота — разные моменты. Учтите инерцию, покрытие, массу и обзор передней камеры. Эта версия не обнаруживает препятствия и не останавливается перед ними автоматически.
