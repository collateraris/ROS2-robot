# Неделя 1: Gazebo → LiDAR → RF2O → SLAM → Nav2

Для ПК с установленной Ubuntu начни с [подробной первой недели на Ubuntu-ПК](WEEK01_UBUNTU_RU.md).

Для ПК с Windows и Raspberry Pi смотри [пошаговый маршрут WSL2 + отдельная проверка C1](WEEK01_WINDOWS_RU.md). Этот файл описывает общую Linux-часть.

Цель недели — воспроизводимый проезд между двумя точками в симуляции и понимание каждого источника координат. Реальный робот остаётся без энкодеров. Симуляция повторяет его сенсорную схему, но её идеальная механика и задержки ещё не являются измерениями настоящего шасси.

## 1. Подготовка

Рекомендуемая система — Ubuntu 24.04, ROS 2 Jazzy, Gazebo Harmonic. Официальная связка устанавливается пакетом `ros-jazzy-ros-gz`; инструкции проверены по [Gazebo ROS installation](https://gazebosim.org/docs/harmonic/ros_installation/).

После основной установки проекта открой новый терминал без активного venv/Conda.
Сборка ROS выполняется системным Python; окружение проекта включается после неё:

```bash
cd ~/robot/room_robot_v5_four_weeks
bash scripts/install_sim.sh
bash scripts/build_ros.sh week01
bash scripts/setup_python.sh base
source scripts/env_robot.sh
```

В каждом следующем терминале перед командами этой недели выполни:

```bash
cd ~/robot/room_robot_v5_four_weeks
source scripts/env_robot.sh
```

Если распаковал проект в другой каталог, замени путь. Скрипт подключает ROS и
overlay, активирует `.venv` и добавляет исходники проекта в `PYTHONPATH`.

Симуляция рассчитана на ПК. Нужен работающий графический драйвер: GPU LiDAR и RGB-камера используют Ogre2. Режим `gui:=false` убирает окно, но не отменяет рендеринг; headless-режиму нужен EGL и доступ к GPU.

## 2. Посмотреть сенсоры и карту

```bash
ros2 launch room_sim sim.launch.py start_mission:=false
```

Откроются Gazebo и RViz. В мире одна четырёхколёсная модель робота, комната с мебелью и геометрический манекен. **Манекен — proxy для геометрии и столкновений. Он не является достоверным тестом распознавания человека моделью GroundingDINO.** Для проверки настоящего детектора далее нужны подходящие реальные изображения или проверенные реалистичные модели.

Движение по умолчанию запрещено до явного ARM. Закрытая/поставленная на паузу симуляция не должна оставлять ненулевую команду: адаптер использует watchdog по монотонному времени.

В отдельных терминалах проверь:

```bash
ros2 topic hz /scan
ros2 topic hz /camera/image_raw
ros2 topic echo /room_base/odom_status
ros2 topic echo /room_base/odom_healthy
ros2 run tf2_ros tf2_echo odom base_link
```

Ожидаемые частоты: LiDAR 10 Гц, камера 15 Гц. Фактическая частота зависит от скорости симуляции. У здоровой системы `/room_base/odom_healthy` становится `true` после нескольких согласованных сканов и оценок RF2O. Если это не произошло, не подменяй одометрию истинной позой симулятора: сначала исправь причину.

| Данные | Топик | Для чего |
|---|---|---|
| Скан 360°, 720 лучей | `/scan`, frame `laser` | RF2O, SLAM, препятствия |
| RGB и калибровка | `/camera/image_raw`, `/camera/camera_info` | Восприятие на неделе 2 |
| Сырые позы RF2O | `/odom_rf2o` | Вход guard |
| Проверенная одометрия | `/odom` | Рабочая навигация |
| Карта | `/map` | SLAM и Nav2 |
| Истинная поза Gazebo | `/sim/odom`, frame `sim_world` | Только оценка ошибок |
| Реальные контакты бампера и колёс | `/sim/contacts` | Столкновения; контакты колёс с полом подтверждают работу сенсоров |

Gazebo публикует контактные сообщения только при реальном контакте. Поэтому четыре колёсных сенсора также передают в `/sim/contacts` контакты с полом; evaluator использует их для проверки доступности потока и исключает пол/self из числа столкновений. В воздухе сенсор не обязан публиковать сообщения.

Поза `/sim/odom` задана в координатах мира и включает стартовое положение модели. Её нельзя соединять с рабочими `/odom` и `/tf`. В модели также существуют Gazebo-каналы колёсной одометрии; ROS bridge их не экспортирует.

## 3. Первый A → B

Для автоматического примера **только в симуляции** перезапусти launch с явным разрешением автономного испытания:

```bash
ros2 launch room_sim sim.launch.py start_mission:=false simulation_autonomy:=true
```

Этот параметр отменяет необходимость постоянно держать операторскую кнопку, но не выполняет ARM. Дождись `odom_healthy=true`, затем:

```bash
ros2 run room_sim goal_ab --arm-simulation \
  --goal 0.0 0.0 0.0 --goal 1.4 0.0 0.0
```

Скрипт проверяет свежий маркер симуляции, режим выхода, единственного провайдера ARM и параметры адаптера. Он проверяет симуляцию перед каждой из двух целей `NavigateToPose` в `map`. Цель отправляется при остановленном приводе; ARM запрашивается только после принятия цели, свежей ненулевой `/cmd_vel_safe` и положительного свежего health. Если цель уже достигнута, как начальная `(0, 0, 0)`, она завершается без ARM. На каждую новую цель допускается один запрос ARM; после watchdog/ESTOP внутри той же цели скрипт не перевключает движение. Между целями и в конце выполняется STOP. При timeout/ошибке скрипт сразу инвалидирует сессию и запрашивает STOP, отменяет принадлежащие ему цели, включая позднее подтверждённые, ограниченное время ждёт завершения и повторяет STOP. Если транспорт не подтвердил отмену, он дополнительно фиксирует аварийный стоп: перед сбросом latch нужно очистить или перезапустить Nav2. Простого ARM недостаточно. Координаты примера относятся к исходной комнате; после изменения мира выбери свободные точки на построенной карте.

Для ручного режима оставь `simulation_autonomy:=false`, открой `python -m robot_extras.task_operator`, удерживай зелёную кнопку и нажми A для ARM. Проезд можно запускать командой `goal_ab` без `--arm-simulation`. Отпускание кнопки останавливает и требует повторного ARM.

Остановка из терминала:

```bash
ros2 service call /room_base/stop std_srvs/srv/Trigger '{}'
```

## 4. Сохранить карту

```bash
mkdir -p data/maps
ros2 run nav2_map_server map_saver_cli -f "$PWD/data/maps/room" \
  --ros-args -p use_sim_time:=true
```

Следующий запуск с картой:

```bash
ros2 launch room_sim sim.launch.py mode:=localization \
  map:="$PWD/data/maps/room.yaml" start_mission:=false
```

В локализации AMCL требуется корректная начальная поза. Укажи её в RViz инструментом `2D Pose Estimate`; не используй `/sim/odom` как автоматическую подсказку локализатору при сравнении алгоритмов.

## 5. Что проверить к концу недели

- Есть связная цепочка `map → odom → base_link → laser/camera_link → camera_optical_frame`.
- RF2O публикует позу по новым сканам; истинная поза Gazebo не попадает в планировщик.
- A → B проходит по свободному маршруту, а STOP, потеря deadman и устаревшие сенсоры дают нулевой выход `/sim/cmd_vel`.
- После ошибки/восстановления данных движение не включается само. При latch в RF2O/guard перезапусти сценарий и заново инициализируй локализацию. Пауза Gazebo дольше watchdog также может потребовать перезапуска.
- Карта сохранена, повторный запуск с AMCL проверен отдельно.

Список команд не означает, что проверка на Gazebo уже выполнена за тебя. В среде подготовки отсутствовал ROS2/Gazebo runtime: здесь проверены исходники, XML, конфигурация, конструирование launch и чистая логика watchdog. Сборка Jazzy, рендеринг и реальные проезды требуют запуска этих команд.

Файлы недели: `room_sim/launch/sim.launch.py`, `room_sim/models/room_robot/model.sdf`, `room_sim/urdf/room_robot.urdf`, `room_sim/room_sim/drive_adapter.py`, `room_sim/room_sim/goal_ab.py`. Тонкий пример запуска также находится в `weeks/week01/go_a_to_b.py`.
