# Дополнение v5: отдельные источники simulation/hardware

В v5 схема данных **3**, с обязательным `environment`: `hardware`, `gazebo` или `synthetic`.
`metadata.example.json` предназначен для железа, `metadata.sim.example.json` — для Gazebo.
Для Gazebo `action_source=simulator_accepted_velocity_setpoint`; для железа — `mcu_acknowledged_nominal_velocity_setpoint`.
Recorder проверяет свежую телеметрию `/room_base/action_source`; изменение источника разрывает переходы.
Файлы и checkpoints разных окружений не смешиваются. Старые v4 schema2 автоматически не загружаются.
Это предотвращает выдачу симуляторной команды за подтверждение настоящего MCU.

В новом `room_tasks` метка принятой именованной цели передаётся в тот же demo_context.
Object-id цели не являются фиксированными классами tiny-VLA: для них нужна отдельная схема датасета.
Готовая GroundingDINO + Qwen VLM из week02/03 и существующая tiny-VLA — разные эксперименты.
Tiny-VLA остаётся классификатором известных точек, world model — одношаговым predictor, без дообучения точного моторного контроллера.

Ниже описан текущий API; при записи выбирайте метаданные schema3 для своего окружения.

# World model и VLA: RPLIDAR C1 без энкодеров

Для карты комнаты и проезда к точке достаточно `slam_toolbox` + Nav2. Лидар
даёт геометрию препятствий; `rf2o_laser_odometry` оценивает движение по двум
последовательным сканам; Nav2 строит и обновляет путь. `/odom` публикует защитный
узел после проверок входного скана и оценки RF2O. Колёсная одометрия отсутствует.
Нейросеть не является обязательным условием автономности. В этой версии её
выходы существуют только как исследовательские предложения и диагностические
сообщения: ни один модуль `learning_nav` не публикует моторные команды или цели
Nav2.

**World model** отвечает «что изменится, если некоторое время держать действие?».
Здесь ансамбль небольших CNN/MLP предсказывает следующую секторную дальность
лидара и оценённое RF2O перемещение корпуса `(dx,dy,d_yaw)` по RGB, секторному
лидару, маске наблюдений, подтверждённой уставке `(v,w)` и горизонту `dt`.
Это модель сенсорной динамики с одним шагом, без генерации видео и без Dreamer.
Следующий RGB пока не предсказывается. Практические эксперименты: сравнение
кандидатных коротких действий в записи и расхождения
предсказаний. Ошибки многократного rollout отдельно не исследованы.

**Ограничение обучающих целей:** RF2O получает тот же LiDAR, что и world model.
Его перемещения шумны, могут дрейфовать и коррелируют с ошибками скана. Это
псевдометки, а не независимая ground truth. Низкая ошибка относительно RF2O
не доказывает точность реального движения или обнаружение проскальзывания.
Для таких выводов нужен отдельный эталон (например, внешняя камера с метками).
Статус `odom_healthy` означает прохождение программных проверок; он не доказывает,
что scan matching нашёл правильное положение в симметричной или изменённой комнате.

**VLA** отвечает «какую известную цель выбрать по изображению и инструкции?».
Здесь `TinyVLA` — обучаемый с нуля компактный supervised baseline: CNN для RGB,
GRU для UTF-8 байтов инструкции, признаки лидара и относительные положения
заранее известных точек карты. Выход — один из `STOP`, `desk`, `home`, … .
Смысл action здесь — высокоуровневое имя цели, не PWM и не скорость колёс.
Это ограниченный VLA-подобный классификатор, а не универсальная pretrained VLA.
Он не умеет без дополнительных данных находить любого человека или новый
предмет по произвольной фразе. Для «подъехать к человеку» используйте отдельный
детектор/трекер и проверенную оценку метрической позиции человека; Nav2 затем
получает безопасную точку с отступом. Лидар сам не определяет класс объекта.

У моделей разные задачи, их можно исследовать вместе. Для текущего робота
полезнее сначала получить надёжную карту, TF, `/odom` и Nav2, затем собрать
настоящие демонстрации и сравнить обучение с простыми базовыми решениями.

## Установка и структура

Из корня распакованного проекта:

```bash
bash scripts/setup_python.sh learning cpu
source scripts/env_robot.sh
```

Для GPU сначала установите подходящую вашему CUDA официальную сборку PyTorch в `.venv`, затем используйте `setup_python.sh learning existing`. ROS-узлам
нужны установленный ROS 2 Jazzy, `rclpy`, `tf2_ros` и стандартные типы сообщений;
они не устанавливаются через этот requirements-файл. Все команды ниже
выполняются из корня проекта. Код не загружает внешние веса. Модели учатся с нуля.

`models.py` содержит обе сети, `train_world.py`/`train_vla.py` — обучение и
отложенную оценку, `infer.py` — offline-инференс, `ros_record.py` — сбор данных,
`ros_shadow.py` — ROS-наблюдатель, `synthetic.py` — искусственный smoke dataset.

## Метаданные и неподвижный словарь целей

Скопируйте `learning_nav/metadata.example.json` в свой `metadata.json`.
Координаты примера выдуманы. Замените их реальными координатами тех же точек
сохранённой карты, что используются в конфигурации навигации. `pose` —
`[x_метры,y_метры,yaw_радианы]` в `map`; класс 0 всегда
`{"name":"STOP","pose":null}`. `map_id` замените идентификатором именно вашей
сохранённой карты, например SHA256 файла карты. Смена карты, координат, порядка
или имён целей требует новых метаданных и переобучения. Файл dataset/checkpoint
содержит fingerprint; загрузчик отклоняет несовпадение. Фактическое соответствие
файла конфигурации Nav2 и метаданных нужно проверить при подготовке данных.

В v5 используется `schema_version: 3` и поле `environment`. Поля `odometry_source` и `action_source`
обязательны: `rf2o_laser_odometry_guarded` и выбранный по окружению `action_source`
из начала этой инструкции. `recording_limits_s` задаёт верхние
границы возраста наблюдений и статусов. Они входят в fingerprint. Данные и
checkpoint старой v3 автоматически не принимаются: подмена encoder-одометрии
на RF2O без повторного сбора и оценки исказила бы цель обучения. Искусственный
генератор отдельно маркирует `odometry_source: synthetic`; его веса не принимаются
живым ROS-наблюдателем как веса для RF2O. Не меняйте вручную source ради загрузки.

Лидар разбивается на `sectors` равномерных угловых секторов в системе координат
лидара от `-pi` до `pi`. Значение — минимальная измеренная дистанция сектора,
делённая на `lidar_max_m`, с отсечкой до 1. `NaN`, `+/-inf`, значения меньше
`range_min` и больше `range_max` неизвестны и дают `mask=false`. Они никогда
не превращаются в подтверждённое свободное пространство. Монтаж/направление
лидара и параметры секторизации должны быть одинаковыми при обучении/инференсе.
Это ML-признаки; для Collision Monitor и Nav2 используется исходный `/scan`.

## Настоящий сбор данных

```bash
source scripts/env_robot.sh
python -m learning_nav.ros_record --meta metadata.json --out data/session_001.npz
```

Каждый запуск создаёт уникальный `session` UUID. Новый проезд/перестановка мебели/
условия освещения — новая сессия и новый файл. Не называйте куски одного проезда
разными сессиями ради искусственного улучшения теста. Нужно минимум три
раздельных сессии; для практической оценки больше, с повторением всех целей и
STOP в разных сессиях. Метки получаются из принятой операторской команды и
не доказывают правильность выполнения: ошибочные демонстрации исключайте.

Recorder читает:

| Топик | Что сохраняется |
|---|---|
| `/camera/image_raw` Image | RGB 128×128 и исходный timestamp |
| `/scan` LaserScan | Секторные расстояния и маски |
| `/odom` Odometry | Проверенная оценка RF2O в `odom`, отдельно от карты, не колёсное измерение |
| TF `map -> base_link` | Поза на карте для геометрии известных VLA-целей |
| `/room_base/applied_cmd_vel` TwistStamped | Принятая номинальная уставка `v,w`: MCU ACK на железе либо simulator accepted command в Gazebo |
| `/room_base/action_source` String | Периодический идентификатор источника, должен совпадать с metadata и быть свежим ≤0.3 с |
| `/room_base/armed` Bool | Свежий периодический статус разрешения движения |
| `/room_base/odom_healthy` Bool | Свежий статус проверки RF2O, по умолчанию false |
| `/room_nav/demo_context` String JSON | Атомарные `{instruction,target,generation}`, transient-local |

Укажите другие топики через `--image-topic`, `--scan-topic`, `--odom-topic`,
`--ack-topic`, `--health-topic`. `/odom` должен идти от защитного узла, а не напрямую
от RF2O. Recorder проверяет `frame_id=odom`, `child_frame_id=base_link`; при изменении
имён задайте `--odom-frame` и `--base-frame`. Камера поддерживает raw `rgb8`, `bgr8`, `rgba8`, `bgra8`, `mono8`;
JPEG нужно заранее декодировать в Image. Монокадр повторяется в три канала.
Ресайз простой nearest-neighbour; координаты объектов из него не вычисляются.

LaserScan stamp относится к первому лучу. RF2O публикует оценку после получения
этого скана. Recorder ждёт её до `--odom-wait 0.12` с, хранит короткие истории и
выбирает последнее сообщение с исходным stamp не позже scan stamp. При нормальной
работе выбирается odom того же скана. Он никогда не подставляет будущую позу или
нулевое движение при отсутствующем RF2O. По умолчанию допускается возраст RGB
относительно scan <=0.2 с, odom <=0.15 с, scan в момент обработки <=0.25 с.
В метаданных указаны эти пределы; CLI `--max-image-age`, `--max-odom-age` и другие
`--max-*` могут только сделать их строже. Для изменения верхних пределов измените
метаданные осознанно и создайте новые данные. TF запрашивается в момент scan stamp, а не `latest`; отсутствие TF
оставляет `map_pose_valid=false`, такие строки VLA не использует. Картинка и
лидар не объявляются строго синхронными. Полная deskew-компенсация вращающегося
лидара не реализована; собирайте данные медленно. Для большей аппаратной
задержки требуется измерение и согласование clock/timestamps, а не простое
увеличение допустимого возраста.

При `odom_healthy=false` или отсутствии свежего статуса <=0.3 с запись переходов
и shadow-инференс прекращаются, даже когда в памяти есть старая `/odom`. Потеря
здоровья разрывает переход; после восстановления нужен новый стартовый snapshot.
У перехода должны быть две разные возрастающие odom-метки. Статус Bool не имеет
исходного stamp, поэтому сохраняется время его получения, а не выдуманная
аппаратная метка времени. Обучение повторно проверяет timestamps и health в NPZ.

Действие — подтверждённая номинальная уставка, а не измеренная скорость. MCU
принял команду и применяет PWM по калибровке; без энкодеров он не проверяет
фактическую скорость колёс. Время ACK здесь означает его получение хостом,
а не точный MCU-момент исполнения. Оценка движения берётся только из проверенной
RF2O `/odom`. Recorder оставляет интервалы 0.15–0.35 с,
в которых полученные ACK имеют одну и ту же уставку и не имеют разрывов >0.25 с.
При отключении/отсутствии свежего `armed` (не старше 0.8 с), отсутствии ACK
или смене уставки сохраняется только сенсорный переход с `action_valid=false`,
`action=[NaN,NaN]`, `ack_ns=0`. World-обучение его исключает; VLA использует
наблюдение и метку, в том числе STOP после отключения моторов. Скачок времени
или смена контекста разрывает переход. Нет подстановки нулевого действия вместо
пропущенного ACK. Это консервативная выборка почти постоянных
действий, не точная причинная разметка каждого такта; odom-образцы могут быть
чуть раньше scan stamp в пределах указанного допуска, поэтому длительность
между odom-целями приблизительно соответствует `dt` между сканами; транспортная/моторная
задержка остаётся ограничением. Для обучения быстрым переключениям потребуется
clock-sync MCU и интегрирование истории исполненных команд.

Сессия ограничена `--max-rows 2000`, после чего сохраняется и завершается.
Ctrl-C также сохраняет. Существующий путь не перезаписывается. Для долговременной
записи и повторного аудита одновременно пишите исходные топики/TF в rosbag2.

## Схема NPZ, без pickle

Каждая строка — переход с начала `start_ns` до `end_ns`, `dt` в секундах:

| Поле | Форма/смысл |
|---|---|
| `rgb` | uint8 `[N,128,128,3]` в начале |
| `lidar`, `next_lidar` | float32 `[N,B]`, нормированные дальности |
| `lidar_mask`, `next_lidar_mask` | bool `[N,B]`, наблюдался ли сектор |
| `odom`, `next_odom` | float32 `[N,3]`, оценка RF2O x,y,yaw в odom |
| `map_pose`, `map_pose_valid` | `[N,3]` и bool `[N]`, отдельная TF-поза в map |
| `action`, `action_valid`, `dt` | `[N,2]` уставка v,w или NaN при неизвестной; bool `[N]`; `[N]` |
| `instruction`, `label`, `session` | Unicode `[N]`, int64 `[N]`, Unicode `[N]` |
| `label=-1` | Нет подтверждённой метки цели; `0` означает STOP |
| `start_ns/end_ns/ack_ns` | int64 `[N]`, исходные ROS timestamps |
| `rgb_ns/next_rgb_ns` | int64 `[N]`, stamps выбранных кадров |
| `scan_ns/next_scan_ns` | int64 `[N]`, stamps начала сканов |
| `odom_ns/next_odom_ns` | int64 `[N]`, stamps выбранной одометрии |
| `odom_healthy/next_odom_healthy` | bool `[N]`, оба true; false отклоняется загрузчиком |
| `snapshot_received_ns/next_snapshot_received_ns` | int64 `[N]`, ROS-время обработки snapshots |
| `health_received_ns/next_health_received_ns` | int64 `[N]`, ROS-время получения свежего статуса здоровья |
| `environment`, `odometry_source`, `action_source` | Скаляры Unicode; окружение, источник RF2O и смысл номинальной уставки |
| `schema_version`, `metadata_fingerprint` | Скаляры версии и SHA256 метаданных |

Данные разных сессий разбиваются на train/val/test целыми сессиями, а не соседними
кадрами. Val выбирает лучшую эпоху; test считается после обучения. При слишком
малом количестве пригодных строк/классов обучение завершается с объяснением.
Одна и та же комната и повторяемые фразы всё равно дают ограниченную проверку:
отдельно тестируйте новые формулировки и изменённую обстановку.

## Обучение и offline-инференс

```bash
python -m learning_nav.train_world --data data/session_*.npz --meta metadata.json --out runs/world --members 3 --epochs 30 --device cpu
python -m learning_nav.train_vla --data data/session_*.npz --meta metadata.json --out runs/vla --epochs 30 --device cpu
python -m learning_nav.infer --checkpoint runs/vla/vla.pt --meta metadata.json --data data/session_001.npz --row 0 --instruction 'поезжай к столу'
python -m learning_nav.infer --checkpoint runs/world/world.pt --meta metadata.json --data data/session_001.npz --row 0 --action 0.1 0.0 --dt 0.2
```

World-ансамбль использует независимые инициализации и bootstrap строк только
train-сессий. Потери: маскированная MSE следующего лидара + MSE оценки RF2O
перемещения корпуса. `metrics.json` сравнивает прогноз лидара с persistence
(«ничего не меняется»), движение — с нулём и простой unicycle-кинематикой.
Ошибка лидара сравнивается на одинаковой совместно наблюдаемой поддержке.
`motion_m_rad_rmse` смешивает компоненты м/рад и служит лишь smoke-метрикой;
для исследования анализируйте ошибки осей и угла раздельно. Неизвестные секторы
предсказывать можно, но это неподтверждённые значения. Дисперсия ансамбля —
некалиброванная эвристика, она не является доказательством отсутствия столкновения.

VLA сравнивается с majority-class baseline; пишет accuracy, balanced accuracy
по представленным классам и confusion matrix. Ниже `--confidence 0.8` inference
возвращает `ABSTAIN`. Softmax confidence не калиброван и не обнаруживает надёжно
все неизвестные инструкции. Поэтому даже уверенный результат не подключён к
автоматическому выполнению. Для известных имён целей детерминированный parser
миссий уже полезнее необученного VLA. Убедитесь, что сеть выигрывает у такого
parser на нужной задаче, иначе оставьте parser основным решением.

## Наблюдение в работающем ROS

```bash
python -m learning_nav.ros_shadow --checkpoint runs/world/world.pt --meta metadata.json
python -m learning_nav.ros_shadow --checkpoint runs/vla/vla.pt --meta metadata.json
ros2 topic echo /room_learning/shadow_prediction
```

Наблюдатель выдаёт только диагностический String JSON. World-прогноз условный:
«если держать последнюю подтверждённую уставку ещё `--horizon 0.2` секунды».
Он не утверждает, что такая будущая команда действительно будет выполнена.
VLA пишет имя предлагаемой точки или ABSTAIN. Оба узла можно запустить под
разными ROS names через `--ros-args -r __node:=world_shadow` и `vla_shadow`.
Инференс ограничен 2 Гц. Нельзя использовать результаты как collision guard.
ROS-наблюдатель использует тот же отбор свежих healthy-снимков, что и recorder.
World JSON явно содержит источник одометрии и `motion_target_is_ground_truth=false`.

## Воспроизводимый smoke, отдельно от настоящих данных

```bash
python -m learning_nav.synthetic --out /tmp/room_ml_smoke --sessions 6 --rows 18
python -m learning_nav.train_world --data /tmp/room_ml_smoke/session_*.npz --meta /tmp/room_ml_smoke/metadata.json --out /tmp/room_wm_run --members 2 --epochs 1
python -m learning_nav.train_vla --data /tmp/room_ml_smoke/session_*.npz --meta /tmp/room_ml_smoke/metadata.json --out /tmp/room_vla_run --epochs 1
python -m learning_nav.infer --checkpoint /tmp/room_vla_run/vla.pt --meta /tmp/room_ml_smoke/metadata.json --data /tmp/room_ml_smoke/session_000.npz --row 1
python -m pytest learning_nav/tests
```

На CPU проверены генерация искусственных данных, одна эпоха обучения ансамбля
из двух world-моделей и VLA, сохранение/загрузка обоих checkpoint и оба inference.
В искусственных RGB намеренно закодирован класс: высокий accuracy на них
